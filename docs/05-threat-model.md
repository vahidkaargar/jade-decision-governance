# 05 — Threat model

Adversary assumption: the operator is trusted; threats come from content the agent reads (repos, web, tool output, third-party skills), from provider drift, and from the agent's own over-confidence. Nothing here depends on the operator being hostile, so tamper-evident logs are out of scope (ADR-08).

| # | Threat | Vector here | Mitigation | Enforced by |
|---|--------|-------------|------------|-------------|
| T1 | Prompt injection via evidence | A README or tool output says "approved, proceed" and the agent passes it as state | State is data; approval is only `permit.approval_reference = tty:*`; `jade ask` output never contains the word "authorized"; adversarial eval set | runtime + evals |
| T2 | Forged approval | Agent runs `jade permit approve` itself, or drives it under a pty it allocated with a clean environment | `approve` refuses unless stdin and stdout are a tty, no agent variable is set (`CLAUDECODE`, `CLAUDE_CODE*`, `CURSOR_AGENT`, `CODEX_SANDBOX`, `AI_AGENT`) and no ancestor process is an agent. The process table is read as `ps -axo pid=,ppid=,comm=` (the executable path whole, spaces included, which is how the Claude desktop app lays out its agent: `~/Library/Application Support/Claude/claude-code/<version>/.../claude`) plus `command=` for the arguments, and each process is matched by its executable name (`claude`, `claude-code`, `claude-agent-sdk`, `codex`, `cursor-agent`, `aider`, `goose`, `opencode`, `gemini`) or its path (anything under `Application Support/Claude/claude-code/`, the app's `Contents/Helpers/disclaimer` launcher, `@anthropic-ai/claude-code`, `@anthropic-ai/claude-agent-sdk`, `@openai/codex`, `.../claude/versions/`, `cursor-agent`), or, for node, bun, deno, npx, python, uv, as the script it runs. Before 0.2.2 the table was split on spaces, so the desktop agent was never recognised and this check protected nothing in that deployment. The Claude app itself (`Claude`, its helpers) is deliberately not an agent, so a human's terminal panel inside it can approve; only the executable and the script an interpreter runs are matched, never other words on the command line, so a human shell under `~/claude-code/` is not an agent. The table is read through one function (`util.read_process_table`) that tests replace with a synthetic tree; it is refused when the table cannot be read or does not list this process); `-y` is not accepted at any level and the human types a code taken from the plan hash; PreToolUse blocks the command in every spelling it can read (SI-09, anchored to the approving invocation and not to the words `jade` or `approve` alone: path-qualified, `env`, `uv run`, `python -m jade`, `python -m jade.cli`, `script`, `xargs`, quoted or split with expansions, `permit approve` as a bare word pair, `$J permit approve`, `jade permit $X`, an alias, function or symlink to the installed launcher, `ap=approve; jade permit $ap`). `gh pr review --approve`, `ACTION=approve ./deploy.sh`, `jade permit approve` with `--help`, `python -m jade.cli check` and `pytest -k jade` are not blocked. **Session leader (W-37):** `is_human_tty` also asks `util.tty_session_refusal`. This process must be in a session whose leader is an interactive shell: stdin is the controlling terminal of its own session (`os.tcgetpgrp` raises for a pty slave that was handed down without `setsid`), the leader (`os.getsid`, read in the process table) is `sh`, `bash`, `zsh`, `dash`, `ksh`, `fish`, `tcsh`, `csh`, `nu`, `elvish`, `xonsh` or `ash`, a login shell spelled `-zsh` included, and it was not started with a command string (`-c`, also `-lc` and `-ic`), `--command` or a script file, and the ancestry of the leader is no agent either (a process that double-forks away keeps its session, so the leader's parents still show the harness). The refusal names the leader (`the leader of its session (pid N) is not an interactive shell: it is python3, not an interactive shell`), so a human whose terminal is built differently (a `tmux new 'jade permit approve'`, an IDE that starts `sh -c`) sees why and runs the command from an interactive shell instead; there is no switch, because a switch in the environment or in a file the agent can write is what T19 closes. The verified variant below (`setsid`, double fork, `pty.fork()`, stripped environment) is refused by it: the process `pty.fork()` starts leads the new session and is `jade` or `python`, not a shell (run on this machine 2026-11-09 with a real pty: `pty.fork()` of `python3`, and of `sh -c`, are refused with the leader named; the same command typed into a `zsh -i` that `pty.fork()` started is refused through the ancestry of the leader, while the agent is its ancestor). **Residual, not closed:** `is_human_tty` is a heuristic for "not obviously an agent". An agent that starts a genuine interactive shell on a pty it holds (`pty.spawn(['zsh', '-i'])`, `expect`, `script` without a command), types `jade permit approve` into it, and detaches from its process tree (double fork, reparented to launchd) satisfies it, and an agent that can run arbitrary code as the same user can also write the ledger directly (T19). Variant verified in the second review and refused since W-37: `setsid` plus a double fork (reparented to launchd), `pty.fork()` and a stripped environment ended with the permit ISSUED, principal `human:<user>` and reference `tty:`. Not matched by SI-09 because the command is built at run time: `ap=approve` split across statements, `importlib.import_module('ja'+'de.permits')`, `base64 -d | sh`, a script the agent wrote first. The approval then carries a `human:` principal and a `tty:` reference that the agent forged. Out-of-band approval is the real fix: implemented as the signed backend (W-38 / W-89, docs/10: a separate OS user signs through sudo, the hook verifies against a root-owned anchor), off until a human installs it (W-90); a Touch ID or Keychain key is not feasible on the reference Mac (docs/10 section 3); the HMAC seal on the permit row (T20, `permit-seal.key`) does not help here because the approval itself is what the agent forges | runtime + hook |

Bash creation means a redirect target, `tee`, `touch`, the destination of `cp`/`mv`/`ln`/`install`/`rsync`, `curl -o`/`wget -O`, `tar -x -C` and `unzip -d` into the directory, and a `git clone` whose destination (or current directory, or `-C` directory) is one of them, also through a `cd` earlier in the command, `$HOME`, `~`, `..` segments, a symlinked directory, `sudo`, `env`, `sh -c` and a literal write in a python program. | T4 | Secret exfiltration to provider | Key or token in `-s` state, in a gated command or in an error message | `redact()` before send and before every ledger write (section 3); `--dry-run` shows the redacted payload; `residual()` refuses a call when a token shape survives (distinctive prefixes anywhere, ambiguous ones such as `sk-` at a word boundary or, glued to a word, when the match is mixed-case with a digit); SI-05 block pattern; state capped 32 KiB. **Residual:** a secret with no known shape or key name (W-42). Residual of that: a same-user plain file an agent process could read (the session that wrote the command holds the secret, but another session or a subagent that reads the file does not, and it reads it with the same tools: the file is the exposure the human accepts when they turn the setting on; a Keychain-held copy is decided with W-38, docs/08 4b) | runtime |

| T6 | TOCTOU between permit and execution | Plan changes after approval | The permit binds `plan_hash` = tool, the command or path **as written** (only its ends are trimmed: whitespace inside quotes, heredocs and between lines is part of the command) and the **resolved** working directory (a retargeted symlink is a different plan). At use the hook recomputes it from the actual call and, in one transaction, also checks: the risk level a fresh classification gives the command is not above the permit's, a high or critical command has a human principal and `tty:` approval reference on the permit, `policy_version` is unchanged (a change revokes every open permit), each recorded precondition still holds (for `git push`: the HEAD commit of the repository it runs in), the permit was requested by the same session and agent, and the decision it belongs to is still live. A permit is single-use with a 30-minute TTL. **Content is bound too (W-39).** For a Write, Edit, MultiEdit or NotebookEdit call (the plan hash names the target path only) and for an MCP call that carries a command (the plan hash is the command only) the permit records a `file_sha` precondition when it is requested: the sha256 of everything the call carries, rendered one-to-one (`policy.content_view`: every value of the input in key order under a header with its key path and length, so a value cannot imitate another field). The consume check compares it in the same transaction as the other preconditions and refuses a call whose content differs (`the content of this call differs from the content that was approved`); the permit is not used up, so the content that was approved can still be written. The digest is part of the sealed permit fields. The approval screen shows the content length, the first 12 characters of the digest and the whole content (escaped like a command); content over 20000 characters, or with a secret-shaped value (never stored), is refused at approval, as a command is. The confirmation code the human types is the first 6 characters of the content digest, not of the plan hash (two writes to one path share the plan hash). Two approved contents for one path each use their own permit, and a pending request for other content replaces the older one. A permit requested before this release has no digest and is refused for a content-bound call (docs/09 section 3). An MCP call with no command already hashed its whole input and is unchanged. Not bound: the content of a file a *shell* command writes (the command text is bound; what an interpreter then does with a script file is T18) | hook |
| T7 | Duplicate external side effects | Retry after OUTCOME_UNKNOWN | State machine forbids retry before reconcile; SI-07 at the hook: while a decision for the identical command is OUTCOME_UNKNOWN, or irreversible and still EXECUTING, the gate blocks the command and raises or consumes no permit until `jade decide outcome` reconciles it. "Identical" is the decision's `hold_key` (the canonical gated segments of the command: quoting, escapes, `;`/`&& true` around it, an env or `command` prefix, `sh -c`, a full program path and the cwd do not make it a new command; older rows without a key fall back to `plan_hash`). A different argument list (`fly deploy --app other`) is a different command and raises its own permit; permits are single-use; Jev calls are side-effect free and may be retried | runtime + hook |
| T8 | Stale cache | Cached judgment applied to changed context | A repeat of an identical question (same question id and version, same canonical state and claim) in the same session within one hour (`ledger.DEDUP_TTL_S`) is answered from the earlier call (the window is `dedup.ttl_s` of `policies/routing.yaml`, read by `ledger.dedup_ttl_s()`); a permit or an authorization is never cached because neither is a Jev call. A repeat is served only from an answered original (DONE with exit 0, 3 or 4: an errored or in-flight call is never the anchor, so the next success becomes the original and stays visible to calibration; rows left EVALUATING by a dead process are closed as errors after 10 minutes), is judged in the calibration group of that original (its `resolved_model` is stored with the row) and is never looser than the first verdict. A permit is bound to the exact `plan_hash` (tool, normalised command or path, working directory) and expires after 30 minutes. Open permits are revoked when their decision is cancelled, expires or finishes (same transaction as the transition) and when `policy_version` changes; a changed precondition (git HEAD for a push, the resolved cwd) makes the permit unusable rather than revoked. The `context_changed` edge and event were deleted from the state machine (W-35): the hook consumes a permit and moves its decision to EXECUTING in one transaction, so no decision waits in AUTHORIZED for a changed precondition to act on, and the refusal at use is the protection that exists | runtime |

| T17 | Hook failure fails open | Hook crashes, the ledger is corrupt or locked, the policy or an overlay does not load, git hangs, or the host kills a slow hook (a killed hook is a non-blocking error: the call proceeds) | The PreToolUse gate fails closed. (1) Classification failure: the shipped rules alone are applied; a call they rate high or critical, or that is not clearly read-only (command) or that writes a protected location (file), is blocked; a clearly read-only command and an ordinary file write pass. (2) Ledger failure after classification (corrupt, locked, full): a call at or above the permit floor is blocked, because no permit can be checked; lower risk passes. (3) An unresolved push destination blocks a high-risk call: git timed out, is missing, refused the repository (`dubious ownership`) or could not read it; "no such ref" and "no repository here" are answers, an unresolved branch is never "not main". The git call that resolves it (W-60) ignores system and global config and the agent's `GIT_*` environment, overrides `core.fsmonitor`, `core.hooksPath` and the pager, reads no stdin and does not widen `safe.directory` (so a repository the user trusts only through their own global `safe.directory` is "dubious ownership" to the hook: a high-risk push from it fails closed and no permit clears it; run that session in advisory mode or trust the repository in its own config); "no repository here" is nothing to push from only for a directory that is written literally and exists: a directory written with a variable (`git -C "$R" push`, `cd "$R" && git push`), `GIT_DIR=`/`GIT_WORK_TREE=` in the command and a repository the same command creates (`git clone u r && git -C r push`) are unresolved. (4) Every wait is bounded: ledger lock waits 1.5 s (`hooks.LEDGER_TIMEOUT_S`), a git call 2 s, and the whole handler runs under an alarm of 6 s (`hooks.BUDGET_S`) against the installed host timeout of 10 s; the alarm lands in a policy-free, linear-time fail-safe with the same rule as (1). Advisory mode never blocks; `off` is human-only (SI-09). `jade check` loads the policy and the overlays, so a malformed overlay regex is reported. A malformed overlay therefore blocks every command that is not clearly read-only until `jade check` is run, even one the shipped rules rate low: the overlay is where machine-specific production hosts and paths live, so the shipped rules are not a sufficient floor and the block is deliberate (the message names the error). Low-risk calls fail open by design | hook |
| T18 | Classification gaps | Command built at run time (base64, variable indirection, `eval` of fetched text); tools the matcher does not name (browser and desktop automation MCP tools); text the classifier cannot read (interpreter code that builds its command from pieces, a script read from a path (`bash x.sh`, `python3 x.py`, `./x`), `sed -f`/`awk -f` script files, `eval "$(cat f)"`, `eval "$VAR"`, a directory computed at run time (`cd $VAR`, `git -C "$DIR"`), a script written by an earlier call; brace expansion beyond 2048 words per word; closed in the W-31 pass: `curl \| sh`, `sh -c "$(curl ..)"`, `base64 -d \| sh`, a file the same command downloads and runs, git aliases defined in a config file, `git config alias.*`, a script the same command writes and runs) | Classification is syntactic by design and says so. One canonicalisation step (`jade/shellnorm.py`) runs before every rule and invariant: git global options are removed so each rule sees `git <subcommand>` (`-c alias.*`, `core.sshCommand/pager/editor/fsmonitor/hooksPath`, `--exec-path` and similar are R-15 high); backslash escapes, line continuations, `$'..'` strings and adjacent quotes are resolved; `$(..)` and backticks inside double quotes and unquoted heredoc bodies are extracted; the body of `sh -c`/`eval`, text fed to a shell or interpreter by heredoc, here-string, pipe or process substitution, and the program of `python -c`/`perl -e`/`node -e`/`awk`/`sed 'w ..'` are searched for literal command text (never parsed or run). A tool that carries a shell command is classified by that command like Bash; text typed or piped into a shell through a tool argument (`interact_with_process`, `app_type`, `computer_batch`, `mcp-exec`) is classified as a command too; MCP file-write tools also get the path rules. ## 3. Redaction function (contract)

`redact(text) -> (text', hits)` replaces with `[REDACTED:<kind>]`:

- PEM and PGP private-key blocks, JWTs, `Bearer` tokens, `Authorization:` and `Proxy-Authorization:` values (a bare value must look like a credential, so the prose `authorization: required` is left alone), `Cookie:` and `Set-Cookie:` values;
- vendor token shapes (the `api_key` kind): OpenAI, OpenRouter, Anthropic, GitHub, GitLab, AWS access key ids, Slack (`xox*`, `xapp-`, `hooks.slack.com/services/...`), Discord webhook URLs, Google (`AIza`, `ya29.`, `GOCSPX-`), Stripe (`sk_`, `rk_`, `pk_`, `whsec_`), Twilio `SK...`, SendGrid, PyPI, npm, Hugging Face;
- URL userinfo passwords (an empty user name and a `@` inside the password are covered; a port such as `host:8080/` is not a password);
- assignments, headers and JSON fields whose key names a credential: `password`, `passwd`, `passphrase`, `secret`, `token`, `api key` (also `api-key`, `x-api-key`), `private key`, `access key`, `account key`, `shared access key`, `auth key`, `signing key`, `credentials`, `cookie`, and the whole words `pass` and `pwd` (`DB_PASS`, `pwd=`; not `PASSED`, and `PWD=/path` is a directory); JSON escaped inside a JSON string and `[value]` forms are read; Azure `AccountKey=`, SAS `sig=` and `X-Amz-Signature=` query values;
- command-line credentials: `curl -u user:pw` (also `-uUSER:PW`, `--user=USER:PW`), `mysql -pPW`, `docker`/`podman login -p PW`, `sshpass -p`, `redis-cli -a`, `htpasswd -b`, `mongosh -p`, `unzip -P`, `ldapsearch -w`, `openssl -passin pass:`, `--password PW`, `--token PW`, `--passphrase PW` and the like (the `--name=value` form is an assignment). A short flag is read only behind its own command word in the same command (`ssh -p 2222` is a port); `?key=` and `&key=` query values and `api key: ...` with a space are read too;
- the line printed under `security find-generic-password ... -w` (the Keychain `-w` output, also `-wa`, `-ws`, `-gw`, an absolute path to `security` and `2>/dev/null`; the match is the command line plus the next non-empty line, so a `-w` inside `$(...)`, a pipe or a redirect redacts nothing: there is no output line to hide) and the value after `security add-generic-password ... -w`;
- a bare random token with no prefix and no key name (the `entropy` kind, W-42): a run of 20 to 256 characters of `A-Za-z0-9_+/-` (a trailing `=` or `==` is padding) that has a digit, an upper-case and a lower-case letter, is at most 10% `_` and `-`, is not made of word chunks (over 60% of its length in `Config` or `retry` shaped pieces: a camel-case identifier), has no relative-path segment when it contains `/`, and has a Shannon entropy of at least 3.5 bits per character. It never starts after a word character, `/`, `.`, `_`, `-` or `+`, after `base64,`, `h1:` or `SHA256:`/`SHA1:`/`MD5:`, and never when it begins like an image, zip, SSH public key, certificate or subresource-integrity hash. The twins it must leave alone (git SHAs, UUIDs, SHA-256 file hashes, base64 image headers, paths, identifiers, lockfile checksums, pod names) are in `tests/fixtures/redact_twins.json`. This is a heuristic: it is a `redact()` pass only, `residual()` does not include it (a false refusal would block a legitimate call, and a redaction is cheap to undo by moving the value into a variable);
- non-owner email addresses (not at all for text that stays on this machine: see below).

It is not applied to a value that is plainly not a secret: a key ending in `count`, `tokens`, `length`, `limit`, `name` or `parallelism` (`max_tokens=4096`, `secret_name: db`), a bare type annotation (`api_key: str`, `token: Optional[str] = None`), a placeholder or a reference (`true`, `none`, `required`, `<token>`, `$TOKEN`, `${DB_PASSWORD}`, `"$TOKEN"`, and a fetch from a store: `$(cat f)`, `$(op read ...)`, `$(pass show x)`; `$(echo S3cret)` is not a fetch and is redacted as a whole), a key that names a setting or a location (it ends in `_type`, `_url`, `_ref`, `_file`, `_path`, `_ttl`, `_expires_in`, `_endpoint`, `_header`, `_prefix`, `_kind`, `_scope`: `TOKEN_TYPE=bearer`, `secret_ref: x`), and an `ssh`, `git`, `hg` or `svn` remote (`git@github.com:org/repo.git`). A numeric password (`password=12345678`) is still redacted. Pure, deterministic, idempotent, unit-tested with a fixture corpus of 105 items (`tests/fixtures/redact_corpus.json`, secrets stored in parts, 18 of them bare random tokens), 105 false-positive twins (`tests/fixtures/redact_twins.json`) and a keep-list of non-secret lines (`tests/acceptance/test_redaction_egress.py`, `tests/acceptance/test_entropy_redaction_w42.py`).

`residual(text)` is the second pass: the union of the high-confidence patterns (`private_key`, `jwt`, `api_key`), built from `PATTERNS` so that the two cannot drift. It also looks at dictionary keys and non-string leaves that `redact_obj` does not rewrite. A residual match after redaction blocks the call (exit 6).

**Cost.** Redaction runs on every gated command before the hook's timeout (10 s), on the whole text and before any length cap. Every quantifier that can run past the end of a value is bounded, so a start without an end (`password=[` with no `]`, a flag with no command behind it) costs one pass and the cost is linear: 150 KB of any such shape stays well under the timeout (`test_redaction_is_linear_on_adversarial_text`). A quadratic pattern here is a fail-open route: the host kills a hook that overruns its timeout and the command runs.

**Where it runs.** `jade ask` and `jade ask --dry-run` run the same `ask.prepare` (redaction, the 32 KiB cap, the residual check), so a dry run prints exactly what a real call would send. Error text printed or journaled for an invalid question is redacted (the `--field` error no longer quotes the value). The ledger redacts at its own choke points as well, whoever the caller is (`secrets_only`: email addresses are kept, since this text never leaves the machine): `state_text`, `question_text` (including `jade fast` arguments), event `guard` and `detail`, and every decision and outcome (`decide.scrub`: objective, command, candidate actions, constraints, assumptions, evidence references, verification method, measurements).

**Gated commands.** The permit's review context stores the redacted command and a `redacted` count; the plan hash still covers the raw command, so a retry of the same command still matches. A human cannot check from a redacted text what the hash covers, so `permits.approve` and `permits.review_text` refuse such a permit, and the block message tells the agent to move the secret into an environment variable or a file and ask again (a reference such as `--token $VERCEL_TOKEN` or `TOKEN=$(cat f)` is not a secret, so the retry is approvable). A literal that looks like a credential is unapprovable even when it is not one (`git push origin main:token=abc`: a ref name cannot be told from `token=abc`); that is accepted and rides on W-43. Newly unapprovable: a gated command with a literal credential on its command line (tracked as W-43).

**Retention.** `jade ledger purge --older-than 90d` clears project text and keeps every metric: Jev call state and question text, decision objective, command and evidence references, the command of a permit that is no longer open, and the detail of events. Statuses, hashes, risk levels, rule ids, probabilities, costs and timings stay. The ledger runs with `secure_delete=ON`, and a purge that cleared rows then runs `VACUUM` and a `TRUNCATE` checkpoint, so the cleared text is gone from the free pages of `jade.sqlite` and from the write-ahead log, not only from the rows. **Residual:** the file system may keep freed blocks of the old file (a copy-on-write volume, a snapshot, Time Machine, a backup); only full-disk encryption and the backup policy cover those. The scrub is best effort: it is skipped when another process holds the database, and the next purge repeats it.

**Entropy pass, measured (W-42).** Synthetic random tokens are found at: base-62 20 characters 96%, 24 characters 98%, 32 characters 99%, 40 and 64 characters 100%; base64 with `+` and `/` 93% to 97%; url-safe base64 90% to 97% (the misses are tokens that lack one of the three character classes, or whose slashes or hyphens make them look like a path or a slug); a Twilio-shaped `AC` plus 32 hex 98%. False positives: 0 of the 105 ordinary-text twins, and 0 of the 578 runs of 20 or more characters in the project's own docs, skills, policies and source (951 KB of text, `test_ordinary_repository_text_is_never_flagged`). The rate on the agent's real evidence (the `evals/baseline` dataset) is not measured here. A false positive costs more than a missed hint in one place: a redaction makes a gated command unapprovable (see Gated commands), and the remedy is the one the block message gives, a variable instead of a literal.

**Known limits (accepted risk).** Redaction recognises shapes, key names and, since W-42, a bare random token that has digits, upper-case and lower-case letters. What still passes: a **pure hex or pure lower-case string** (a 64-digit hex key, a 32-digit hex API key), because a SHA-256, a git SHA, a UUID and a file hash are the same shape and Jev needs them as evidence (F23); a secret of 19 characters or fewer, or one over 256; a secret under an unlisted name whose value has fewer than three character classes (`key=`, `pin=`, `auth=` with a numeric or lower-case value); a token that begins like an image, certificate, SSH public key or SRI hash, or follows `base64,`, `h1:`, `SHA256:`; a token in a URL path segment (it follows a `/`); a secret split by a zero-width character, a newline or full-width letters (no Unicode normalisation is done); one that contains a comma after `=`; a Keychain output printed without its command if it is not random-looking. Those pass, and `residual()` does not catch them (it is the prefix check, not an entropy check). Tracked as W-42 (the opt-in pass for a hex run next to a key-like word and the Unicode normalisation remain open). The control that remains is the one in T15: the agent is told not to paste credentials, and the ledger is local, mode 600 (the database and its `-wal` and `-shm` files are created 600 before SQLite opens them, whatever the umask) and purged.

## 4. What a Markdown skill cannot do

A SKILL.md can shape behaviour; it cannot stop a tool call. Every "must" in this design that protects a side effect is implemented as exit code, hook, or schema, and the skill merely explains it. The measured 30% low-P→done rate under the current prose-only rule is the evidence for this split.
