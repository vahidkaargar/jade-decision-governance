# 05 — Threat model

Adversary assumption: the operator is trusted; threats come from content the agent reads (repos, web, tool output, third-party skills), from provider drift, and from the agent's own over-confidence. Nothing here depends on the operator being hostile, so tamper-evident logs are out of scope (ADR-08).

| # | Threat | Vector here | Mitigation | Enforced by |
|---|--------|-------------|------------|-------------|
| T1 | Prompt injection via evidence | A README or tool output says "approved, proceed" and the agent passes it as state | State is data; approval is only `permit.approval_reference = tty:*`; `jade ask` output never contains the word "authorized"; adversarial eval set | runtime + evals |
| T2 | Forged approval | Agent runs `jade permit approve` itself | `approve` refuses when not a TTY or when `CLAUDE_CODE`/`CLAUDECODE` env present; PreToolUse also blocks `jade permit approve` from the agent (R-13-like rule) | runtime + hook |
| T3 | Compromised third-party skill | eran-broder/jev-skills ships fail-open hooks exfiltrating tool output | None installed; inventory §4 documents rejection; `skills-discovery-guard` still active | policy |
| T4 | Secret exfiltration to provider | Key or token in `-s` state | `redact()` before send and store; SI-05 block pattern; state capped 32 KiB | runtime |
| T5 | Authority spoofing by model output | "Jev said 0.98 so it is safe" | SI-01; permits never derived from P; risk rules can only be raised by Jev, never lowered | runtime |
| T6 | TOCTOU between permit and execution | Plan changes after approval | `plan_hash` recomputed from the actual command in PreToolUse; preconditions (git HEAD, file sha) re-checked; permit single-use with 30-min TTL | hook |
| T7 | Duplicate external side effects | Retry after OUTCOME_UNKNOWN | State machine forbids retry before reconcile; SI-07 at the hook: while a decision for the identical command (same `plan_hash`) is OUTCOME_UNKNOWN, or irreversible and still EXECUTING, the gate blocks the command and raises or consumes no permit until `jade decide outcome` reconciles it; permits are single-use; Jev calls are side-effect free and may be retried | runtime + hook |
| T8 | Stale cache | Cached judgment applied to changed context | Cache key includes canonical state; TTL 30 min; authorization never cached. A permit is bound to the exact `plan_hash` (tool, normalised command or path, working directory) and expires after 30 minutes. The `context_changed` edge exists in the state machine but nothing raises it yet, so a permit is not revoked when the repository or file state changes between approval and use (W-35) | runtime |
| T9 | Provider drift / model change | Resolved model string changes silently | Ledger stores resolved model; `MODEL_DRIFT` work item; new snapshot = new calibration group at default thresholds (Q6: no freeze); `jade check` canary question with known answer | runtime + launchd |
| T10 | Benchmark leakage / poisoning | Candidate generator reads protected set; transcript-mined set overlaps live | `protected/` readable only by `jade eval run --protected` (human TTY); split by session hash; candidates record `dataset_versions` | runtime + policy |
| T11 | Reward hacking / proxy gaming | Challenger lowers abstention by always accepting | Pass criteria include unsafe-accept with CI, not only coverage; protected test; human promotion for thresholds | promotion.yaml |
| T12 | Runaway self-modification | Candidate edits safety.yaml or its own promotion rule | `improvement.target_component` enum excludes protected targets; R-13 makes those edits high-risk (permit) | schema + hook |
| T13 | Recursive evaluation DoS | DEEP emits questions that emit questions | `revision_count ≤ 3`, `max_questions_per_request 8`, `max_parallel 4`, deadline 20 s, daily call budget (default 500) with soft alarm | runtime |
| T14 | Escalation fatigue | Every medium decision pings the human | Recommended default; abstention budget tracked; only high/critical require TTY. Batching (`group_window_s`) is designed but not implemented (W-35) | policy |
| T15 | Data retention / privacy | Ledger stores project text | Redaction; state cap; ledger local only (`~/.local/share/jade`), mode 600; `jade ledger purge --older-than 90d` (default, human decision Q7) removes state_bytes while keeping metrics | runtime |
| T16 | Cross-tenant contamination | n/a single tenant | `tenant_scope` constant; revisit if multi-host | — |
| T17 | Hook failure fails open | Hook crashes, the ledger is corrupt or locked, the policy or an overlay does not load, git hangs, or the host kills a slow hook (a killed hook is a non-blocking error: the call proceeds) | The PreToolUse gate fails closed. (1) Classification failure: the shipped rules alone are applied; a call they rate high or critical, or that is not clearly read-only (command) or that writes a protected location (file), is blocked; a clearly read-only command and an ordinary file write pass. (2) Ledger failure after classification (corrupt, locked, full): a call at or above the permit floor is blocked, because no permit can be checked; lower risk passes. (3) An unresolved push destination (git timed out) blocks a high-risk call. (4) Every wait is bounded: ledger lock waits 1.5 s (`hooks.LEDGER_TIMEOUT_S`), a git call 2 s, and the whole handler runs under an alarm of 6 s (`hooks.BUDGET_S`) against the installed host timeout of 10 s; the alarm lands in a policy-free, linear-time fail-safe with the same rule as (1). Advisory mode never blocks; `off` is human-only (SI-09). `jade check` loads the policy and the overlays, so a malformed overlay regex is reported. Low-risk calls fail open by design | hook |
| T18 | Classification gaps | Command built at run time (base64, variable indirection, `eval` of fetched text); tools the matcher does not name (browser and desktop automation MCP tools); text the classifier cannot read (interpreter code that builds its command from pieces, a script read from a path, `curl \| sh`, `-C "$DIR"`, `sed -f`/`awk -f` script files, a directory computed at run time (`cd $VAR`), git aliases defined in a config file; brace expansion beyond 2048 words per word) | Classification is syntactic by design and says so. One canonicalisation step (`jade/shellnorm.py`) runs before every rule and invariant: git global options are removed so each rule sees `git <subcommand>` (`-c alias.*`, `core.sshCommand/pager/editor/fsmonitor/hooksPath`, `--exec-path` and similar are R-15 high); backslash escapes, line continuations, `$'..'` strings and adjacent quotes are resolved; `$(..)` and backticks inside double quotes and unquoted heredoc bodies are extracted; the body of `sh -c`/`eval`, text fed to a shell or interpreter by heredoc, here-string, pipe or process substitution, and the program of `python -c`/`perl -e`/`node -e`/`awk`/`sed 'w ..'` are searched for literal command text (never parsed or run). Other quoted prose and heredoc bodies are not commands; a `#` that starts a word is a comment and ends at the newline whatever a trailing backslash says; `{a,b}` brace lists are expanded (`m{a,}in` is `main`); `eval` and `sh -c` take the joined words of the command (`eval "git" push ...`, nested `sh -c` with POSIX quote escapes, `$0`/`$@` filled from the arguments, `eval "$(echo ...)"`), and the text of every earlier pipeline stage counts as input of a shell reader (`| tee /dev/stdout | sh`, `| xargs sh -c`, `| source /dev/stdin`). One table of verbs (`verb_effects`, `git_effects` in `jade/shellnorm.py`) decides what each `read_only` verb can write or run: it parses operands (`uniq -f 1 in OUT`, `xxd -c 8 in OUT`, `sort --out=`, sed programs against an allow-list, awk programs, `find -exec`) and exec options (`less +!`, `man -P`, `rg --pre`, `bat --pager`, `sort --compress-program`, `git --upload-pack`, `rebase --exec`, `submodule foreach`, `bisect run`, `LESSOPEN`/`PAGER`/`GIT_*` variables); a verb that can write or run something has a copy of its resolved words classified by every rule, so a protected path or `git push` behind an option value is seen; `cd`/`pushd`/`popd` are followed (subshells keep their own directory) so HEAD resolution and relative operands use the directory the command runs in, and relative operands are also tried as absolute symlink-resolved paths against R-01/R-04/R-12/R-13; `rm` flag spellings are folded to `rm -rf`, `git clean`/`branch` delete flags are order-free, and `GIT_SSH_COMMAND`/`GIT_PAGER`/`GIT_CONFIG_*`/`GIT_EXEC_PATH` environment variables are R-15; any Write/Edit input key (`path`, `filePath`, `file` ...) or, failing that, any non-content string value is a target path. The scanner is linear: the current stage is kept as its head and tail, and a work budget of 4 million characters across nested levels degrades the rest to plain text search instead of running past the hook timeout; the `read_only` list admits a verb only without the flag or operand that makes it write; SI-08 parses `git push` arguments (refspec destinations, `HEAD`/`@` resolved against the current branch, `--all`, `--mirror`); Write-tool paths are expanded, symlink-resolved and matched case-insensitively. Non-Bash tools are classified by name (`mcp_tools` in `policies/risk.yaml`, first match): cluster and repository changes, governance wiring (`set_session_permission_mode`, `set_setting`, `set_config_value`, scheduled tasks, MCP profile and server changes, sending to or starting another session), nested executors (`mcp-exec`, `code-mode`, `run_code_unsafe`, `RemoteTrigger`) and file writes are high or critical; a tool with a read-only name is low; a tool whose name says it writes, deletes, executes or sends and that no rule names is high (M-07); any other unnamed MCP tool is medium (M-99: recorded, not gated). A tool that carries a shell command is classified by that command like Bash; text typed or piped into a shell through a tool argument (`interact_with_process`, `app_type`, `computer_batch`, `mcp-exec`) is classified as a command too; MCP file-write tools also get the path rules. Invariants SI-02 and SI-05 are checked on the text a Write, Edit, MultiEdit, NotebookEdit or MCP call carries (new text only, never `old_string`). The matcher is `policy.GATED_BUILTIN` plus `mcp__.*` (Bash, PowerShell, Monitor, Write, Edit, MultiEdit, NotebookEdit, RemoteTrigger); `jade check` flags an installed matcher that is narrower. Agent and Task need no gate: the tool calls a subagent makes run the same PreToolUse hook (the event adds `agent_id`, which is journaled; this was not verified against a live host in this tree: unverified, confirm with `jade ledger` events after a subagent push). CronCreate and CronDelete only schedule a prompt that later runs under the same hooks and are not gated. Built-in tools that did not exist when the matcher was written are not gated until `GATED_BUILTIN` names them. Residual risk is tracked as W-31 and W-34. **No host backstop in some modes:** the earlier statement that Claude Code's own permission prompt is an independent backstop holds only when the host asks. The hook event carries `permission_mode`; with `bypassPermissions` or `auto` (and `acceptEdits` for file edits), in headless `claude -p` runs and in unattended subagents there is no prompt, and JADE's gate is the only gate: every classification gap above is then an unmitigated bypass. JADE records the mode of every gated call (events `gated` and `safety_block`, and the permit scope) and `jade check` prints this limit and how many gated calls of the last 7 days ran without a host prompt. Decision: classification does not tighten in those modes (it is syntactic either way); run unattended agents in advisory mode only when watched, and prefer a sandbox or a separate OS user for agents that run in bypass mode | hook + host |
| T19 | Self-modification of governance wiring | Agent edits hook config, runs `jade hooks`/`jade gate`/`jade permit approve`, or sets `JADE_GATE_MODE`; or edits JADE's own runtime artifacts: the ledger (`jade.sqlite`, `-wal`, `-shm`, `-journal`; permit rows carry no signature, so a row edit would be accepted), `calibration/current.json`, `pins.json`, `~/.config/jade` config and local overlays, the installed package and the uv tool directory, the `jade` and `jev` launchers, the maintain LaunchAgent | SI-09 blocks the commands, R-13 gates the files and Bash writes to them (path text, relative paths after `cd`, symlink-resolved operands, redirects, `sqlite3`, `uv tool uninstall/upgrade/reinstall/install` naming jade, `launchctl bootout/unload/disable` through R-12), and the installers and approval refuse to run without a human terminal. The human-only CLI writes these files from Python, not through a gated tool call, so it is unaffected. **Accepted residual risk:** an agent with an unrestricted shell as the same OS user can write any file that user owns by a route the classifier cannot read (a script it wrote first, a computed path, its own pty). An HMAC on permit rows would need a key the agent cannot read; a Keychain item the same user can read does not qualify, so none is used. Mitigation is outside JADE: a separate OS user or sandbox for the agent (W-34) | runtime + hook |

## 3. Redaction function (contract)

`redact(text) -> (text', hits)`: replaces matches of SI-05 patterns, `Authorization:` header values, `password=`/`token=`/`secret=` assignments, Keychain `-w` outputs, and non-owner email addresses with `[REDACTED:<kind>]`. Pure, deterministic, unit-tested with a fixture corpus (Phase 1). Residual match after redaction blocks the call (exit 6).

## 4. What a Markdown skill cannot do

A SKILL.md can shape behaviour; it cannot stop a tool call. Every "must" in this design that protects a side effect is implemented as exit code, hook, or schema, and the skill merely explains it. The measured 30% low-P→done rate under the current prose-only rule is the evidence for this split.
