# 05 — Threat model

Adversary assumption: the operator is trusted; threats come from content the agent reads (repos, web, tool output, third-party skills), from provider drift, and from the agent's own over-confidence. Nothing here depends on the operator being hostile, so tamper-evident logs are out of scope (ADR-08).

## 3. Redaction function (contract)

`redact(text) -> (text', hits)` replaces with `[REDACTED:<kind>]`:

- PEM and PGP private-key blocks, JWTs, `Bearer` tokens, `Authorization:` and `Proxy-Authorization:` values (a bare value must look like a credential, so the prose `authorization: required` is left alone), `Cookie:` and `Set-Cookie:` values;
- vendor token shapes (the `api_key` kind): OpenAI, OpenRouter, Anthropic, GitHub, GitLab, AWS access key ids, Slack (`xox*`, `xapp-`, `hooks.slack.com/services/...`), Discord webhook URLs, Google (`AIza`, `ya29.`, `GOCSPX-`), Stripe (`sk_`, `rk_`, `pk_`, `whsec_`), Twilio `SK...`, SendGrid, PyPI, npm, Hugging Face;
- URL userinfo passwords (an empty user name and a `@` inside the password are covered; a port such as `host:8080/` is not a password);
- assignments, headers and JSON fields whose key names a credential: `password`, `passwd`, `passphrase`, `secret`, `token`, `api key` (also `api-key`, `x-api-key`), `private key`, `access key`, `account key`, `shared access key`, `auth key`, `signing key`, `credentials`, `cookie`, and the whole words `pass` and `pwd` (`DB_PASS`, `pwd=`; not `PASSED`, and `PWD=/path` is a directory); JSON escaped inside a JSON string and `[value]` forms are read; Azure `AccountKey=`, SAS `sig=` and `X-Amz-Signature=` query values;
- command-line credentials: `curl -u user:pw` (also `-uUSER:PW`, `--user=USER:PW`), `mysql -pPW`, `docker`/`podman login -p PW`, `sshpass -p`, `redis-cli -a`, `htpasswd -b`, `mongosh -p`, `unzip -P`, `ldapsearch -w`, `openssl -passin pass:`, `--password PW`, `--token PW`, `--passphrase PW` and the like (the `--name=value` form is an assignment). A short flag is read only behind its own command word in the same command (`ssh -p 2222` is a port); `?key=` and `&key=` query values and `api key: ...` with a space are read too;
- the line printed under `security find-generic-password ... -w` (the Keychain `-w` output, also `-wa`, `-ws`, `-gw`, an absolute path to `security` and `2>/dev/null`; the match is the command line plus the next non-empty line, so a `-w` inside `$(...)`, a pipe or a redirect redacts nothing: there is no output line to hide) and the value after `security add-generic-password ... -w`;
- non-owner email addresses (not at all for text that stays on this machine: see below).

It is not applied to a value that is plainly not a secret: a key ending in `count`, `tokens`, `length`, `limit`, `name` or `parallelism` (`max_tokens=4096`, `secret_name: db`), a bare type annotation (`api_key: str`, `token: Optional[str] = None`), a placeholder or a reference (`true`, `none`, `required`, `<token>`, `$TOKEN`, `${DB_PASSWORD}`, `"$TOKEN"`, and a fetch from a store: `$(cat f)`, `$(op read ...)`, `$(pass show x)`; `$(echo S3cret)` is not a fetch and is redacted as a whole), a key that names a setting or a location (it ends in `_type`, `_url`, `_ref`, `_file`, `_path`, `_ttl`, `_expires_in`, `_endpoint`, `_header`, `_prefix`, `_kind`, `_scope`: `TOKEN_TYPE=bearer`, `secret_ref: x`), and an `ssh`, `git`, `hg` or `svn` remote (`git@github.com:org/repo.git`). A numeric password (`password=12345678`) is still redacted. Pure, deterministic, idempotent, unit-tested with a fixture corpus of 80 items (`tests/fixtures/redact_corpus.json`, secrets stored in parts) and a keep-list of non-secret lines (`tests/acceptance/test_redaction_egress.py`).

`residual(text)` is the second pass: the union of the high-confidence patterns (`private_key`, `jwt`, `api_key`), built from `PATTERNS` so that the two cannot drift. It also looks at dictionary keys and non-string leaves that `redact_obj` does not rewrite. A residual match after redaction blocks the call (exit 6).

**Cost.** Redaction runs on every gated command before the hook's timeout (10 s), on the whole text and before any length cap. Every quantifier that can run past the end of a value is bounded, so a start without an end (`password=[` with no `]`, a flag with no command behind it) costs one pass and the cost is linear: 150 KB of any such shape stays well under the timeout (`test_redaction_is_linear_on_adversarial_text`). A quadratic pattern here is a fail-open route: the host kills a hook that overruns its timeout and the command runs.

**Where it runs.** `jade ask` and `jade ask --dry-run` run the same `ask.prepare` (redaction, the 32 KiB cap, the residual check), so a dry run prints exactly what a real call would send. Error text printed or journaled for an invalid question is redacted (the `--field` error no longer quotes the value). The ledger redacts at its own choke points as well, whoever the caller is (`secrets_only`: email addresses are kept, since this text never leaves the machine): `state_text`, `question_text` (including `jade fast` arguments), event `guard` and `detail`, and every decision and outcome (`decide.scrub`: objective, command, candidate actions, constraints, assumptions, evidence references, verification method, measurements).

**Gated commands.** The permit's review context stores the redacted command and a `redacted` count; the plan hash still covers the raw command, so a retry of the same command still matches. A human cannot check from a redacted text what the hash covers, so `permits.approve` and `permits.review_text` refuse such a permit, and the block message tells the agent to move the secret into an environment variable or a file and ask again (a reference such as `--token $VERCEL_TOKEN` or `TOKEN=$(cat f)` is not a secret, so the retry is approvable). A literal that looks like a credential is unapprovable even when it is not one (`git push origin main:token=abc`: a ref name cannot be told from `token=abc`); that is accepted and rides on W-43. Newly unapprovable: a gated command with a literal credential on its command line (tracked as W-43).

**Retention.** `jade ledger purge --older-than 90d` clears project text and keeps every metric: Jev call state and question text, decision objective, command and evidence references, the command of a permit that is no longer open, and the detail of events. Statuses, hashes, risk levels, rule ids, probabilities, costs and timings stay. The ledger runs with `secure_delete=ON`, and a purge that cleared rows then runs `VACUUM` and a `TRUNCATE` checkpoint, so the cleared text is gone from the free pages of `jade.sqlite` and from the write-ahead log, not only from the rows. **Residual:** the file system may keep freed blocks of the old file (a copy-on-write volume, a snapshot, Time Machine, a backup); only full-disk encryption and the backup policy cover those. The scrub is best effort: it is skipped when another process holds the database, and the next purge repeats it.

**Known limits.** Redaction recognises shapes and key names. A secret that has neither (a bare hex or base64 string, a value under an unlisted name such as `key=` or `pin=`, a secret split by a zero-width character, a newline or full-width letters, one that contains a comma after `=`, a Keychain output printed without its command) passes, and `residual()` does not catch it. Tracked as W-42. The control that remains is the one in T15: the ledger is local, mode 600 (the database and its `-wal` and `-shm` files are created 600 before SQLite opens them, whatever the umask) and purged.

## 4. What a Markdown skill cannot do

A SKILL.md can shape behaviour; it cannot stop a tool call. Every "must" in this design that protects a side effect is implemented as exit code, hook, or schema, and the skill merely explains it. The measured 30% low-P→done rate under the current prose-only rule is the evidence for this split.
