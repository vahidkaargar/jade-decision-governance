## [Unreleased]

### Fixed
- **Signed approval: independent review findings (W-38, W-89, docs/10 section 4.4).** The verifier and the helper run only absolute root-owned programs (`/usr/bin/ssh-keygen`, `/usr/bin/sudo`): a bare name could resolve to a program in the agent user's own bin directory, and a `ssh-keygen` that exits 0 would have made every forged approval verify. An installed default trust anchor always wins over `JADE_APPROVER_ANCHOR` (a missing override target used to read as "no anchor", a downgrade to terminal approval). The anchor and the helper must sit under directories that belong to root and are not writable by group or others (sticky directories allowed). The helper moved to `/Library/PrivilegedHelperTools/jade-approve-sign` (`/usr/lib/jade/` elsewhere) and ignores its test overrides when run through sudo. `scripts/install-approver.sh` now shows the helper, its sha256 and the sudoers rule and needs `INSTALL` typed, makes the private key as the approver account (never in your temp), creates a hidden `dscl` service account `_jadeapprove` instead of a login account, adds a `!ALL` line so an admin rule cannot read the key, writes the trust anchor last and from the key on every run, and removes a configured `approval_backend` on `--uninstall`. Still untested on a real system. Residuals recorded: a trojaned `jade`/`sudo` that keeps the password (W-91, hardware key), and a consumed permit that SQL can re-arm inside its window (W-92).

### Added
- **Public-release readiness.** `CODE_OF_CONDUCT.md`, issue templates (bug, feature or policy request, private security reports), a pull request checklist, Dependabot for GitHub Actions and uv, a gitleaks config that allows only the fake credentials in `tests/` and `evals/`, a supported-versions and response-time section in `SECURITY.md`, and README and CONTRIBUTING text that no longer says signed approval is unimplemented or that the runtime is 0.2.x. A full-history gitleaks scan found no real secret, and no tracked file names the maintainer's host, home path or address.
- **Signed permit approval: an approval a same-user process cannot make (W-38, W-89; docs/10).** With the approver installed, a high or critical permit is approved by an Ed25519 signature made by a separate OS user through `sudo -u` (your own login password, every time) and verified at use against a root-owned trust anchor with `ssh-keygen -Y verify` (no new dependency). The message names the permit, plan hash, preconditions (content digest), policy version, risk, principal, validity window and nonce; the hook rebuilds it from the row, so a row edited or forged with SQL, a signature from another key, a signature replayed on another permit and an expired window are all refused, even when the seal is re-made. The backend turns on when the anchor exists (an agent cannot delete a root-owned file) or `"approval_backend": "signed"` is configured; with neither, nothing changes. `jade check` has an `approval backend` row; `jade gate enforce` refuses to start without the signed backend when the last 7 days had gated calls with no host prompt, unless `--allow-unsigned` (journaled). `JADE_APPROVER_ANCHOR` (test isolation) is a gate-override variable: SI-11 blocks an agent from setting it and `jade check` reports it. New: `jade/signing.py`, `scripts/jade-approve-sign`, `scripts/install-approver.sh` (human only; untested on a real system), `tests/acceptance/test_signed_approval_w89.py` (20 cases). Not changed: the reveal file (W-84) and the `jade ack` session id (W-81).

### Changed
- **`docker rm -f <names>` is no longer R-12 high (W-66, your decision of 2026-11-13).** Only that exact shape: a plain `docker rm`, `docker rm -f $(...)`, any chain, `docker compose rm|up|down` and every other R-12 action stay high. It now rates low by default. Same decision round: W-62 (branch delete, hard reset, rm -rf of a variable path), W-63 (R-04) and W-64 (R-L01) stay as they are; R-15 on `git -c core.hooksPath` was already high.
- **The test suite is safe to run after the approver is installed (W-93).** `tests/conftest.py` points `signing.DEFAULT_ANCHOR` at a missing temporary file for in-process tests and skips the eleven modules that approve high permits in a subprocess while the real anchor exists (CI and any machine without it still run them). Verified by simulating an installed anchor; not yet run on a host that really has one.
- **SI-11 no longer blocks a scratch `JADE_HOME` or `JADE_CONFIG` prefix in front of a test, lint or jade call (W-48).** `JADE_HOME=$(mktemp -d) JADE_SOURCE=test uv run pytest -q`, `JADE_HOME=/tmp/s jade check --offline` and the other synthetic-payload forms that `skills/jade/SKILL.md` tells an agent to use were blocked, with no permit able to lift it: 821 of the 942 `safety_block` events of the first advisory week. The exemption is one narrow shape: a leading assignment of `JADE_HOME` or `JADE_CONFIG` whose value is `$(mktemp -d)`, empty, or a path under `/tmp`, `/private/tmp` or `/var/folders`, in front of `pytest`, `ruff`, `jade` or `jev` (also behind `uv run` or `python -m`). `JADE_GATE_MODE`, `JADE_POLICY_DIR`, `export`, `env`, a real path, a `..` segment, a variable and any other program stay blocked; SI-09 still blocks `jade permit approve` and the other human-only commands inside the same command. Evidence: `tests/acceptance/test_si11_scratch_prefix_w48.py` (32 cases); the W-71 twin for `JADE_HOME=/tmp/x uv run pytest` now names the real home. Needs a human review before a release because it narrows a safety invariant (docs/05 T19).

The digest is in the sealed fields (a `file_sha` edit breaks the seal). The approval screen prints the content length, digest prefix and the whole content; content over 20000 characters or with a secret-shaped value is refused at approval; the typed confirmation code is the content digest prefix. `find_usable` prefers the permit whose preconditions match, so two approved contents for one path each find their own. - **A patch applied by `patch`, `git apply` or `git am` is classified by the files its headers name (W-37, T19).** The headers (`---`, `+++`, `diff --git`, `rename|copy from|to`, `Index:`, context-diff `***`, quoted names) are read when the patch is a heredoc or here-string of the command (also inside `( )`, `{ }`, `if`, `sh -c '..'`, `bash <<EOF`, `$( )`), a file the same command writes, a file on disk (`< p`, `-i p`, `git apply p`, `cat p | patch`; at most 1 MiB), or an `echo`/`printf`/`cat` piped in; the strip level, `-d`, `--directory` and `git -C` are applied and each target is judged as if a redirect had written it, so R-13, R-16 and R-24 decide. `--check`, `--stat`, `--numstat`, `--summary`, `--cached` and `--dry-run` write nothing. **Newly gated:** a patch that names `.claude/settings.json`, `policies/*`, `AGENTS.md`, `jade/*.py` and the other protected paths. **R-31 label `patch-body` (recorded, not gated, journaled by label only):** a patch whose text exists only at run time (`git diff | git apply -`, `curl .. | patch`, a variable, a glob, a file another command of the line rewrites, a file over 1 MiB). New module `jade/samecmd.py`.
- **A link made by the command that uses it is followed (W-37, T19).** `ln -s ~/.claude /tmp/c && echo x > /tmp/c/settings.json` is the write to `~/.claude/settings.json`: symbolic and hard links, `-t`, a link into a directory, `~` and `$HOME` targets and chains of links are followed by the later commands of the same line, in the directory each runs in. A write before the link exists and a different directory are not through it.
- **R-24 (high): `pyproject.toml` and `uv.lock` of JADE's own checkout (W-37, T19).** `checkout_only`: the file must sit beside a `jade/` package that holds `__init__.py` and `hooks.py`; every other project keeps its `pyproject.toml` free. - **`is_human_tty` also asks for a terminal session led by an interactive shell (W-37, T2).** `util.tty_session_refusal`: stdin is the controlling terminal of this process's session, the session leader is `sh`, `bash`, `zsh`, `fish` or another shell (a login shell `-zsh` included) started without `-c`/`--command` and without a script, and the leader's own ancestry is no agent. It refuses the `pty.fork()` variant verified in the second review (the leader is `jade` or `python`) and names the leader in the message. **Newly refused:** `jade permit approve` and the other human-only commands from a command that is itself the program of a terminal (`tmux new 'jade permit approve'`, an IDE run configuration, `ssh host jade permit approve` without a shell); run them from an interactive shell. Takes effect on the next re-install (docs/08 section 1.1); no switch, by design. The eval runner simulates the human terminal for both probes.

- **Git aliases from a config file are classified by their expansion (W-31).** For a subcommand that is not a built-in git command, one `git config --get-regexp ^alias\.` call (agent `GIT_*` dropped, system and global config read, 2 s, once per directory, two directories at most) gives the alias table, and the expansion (`!` aliases as shell commands, aliases of aliases five levels) is classified as if typed, by every rule and by SI-08: `git p` for `p = push origin main` is a push to the default branch. EOF; bash x.sh`, `tee`, `echo`/`printf` redirected to a literal file, then `bash`, `python3`, `source`, `.` or `./x` on it: the text is classified as if fed to the interpreter by a heredoc (R-03, SI-08 ...). A file that is written and never run, and a string a Python program only prints, stay data. About 40 ms for a 5000-line heredoc.

### Added

- Stricter, so previously allowed commands now need a permit or are blocked (cluster A2): any `launchctl bootout|unload|disable`, `uv tool uninstall|upgrade|reinstall <jade>`, any command or Bash redirect that names `jade.sqlite`, `~/.config/jade`, `~/.local/share/jade`, `calibration/current.json` or the jade tool directory (reads by a read-only verb such as `cat` stay low; `sqlite3 ... jade.sqlite` even for a read is high), `rm/mv/cp/sed ... ~/.local/bin/jade`, any MCP tool whose name starts with set/write/edit/create/update/delete/remove/move/exec/run/send/start/... and that no rule names (high, M-07), `mcp-exec`, `code-mode`, `RemoteTrigger`, a Write/Edit/MCP call whose new text holds a token or a public bind address (SI-05/SI-02 block, no permit can allow it), `policies/loader.py`, `jade/ops.py` and `jade/paths.py` as protected files (so `git add` or `ruff check` naming them is high, see W-32), and a retry of a command whose outcome is unknown (SI-07). While the policy cannot load, everything but a clearly read-only command is blocked.

- Second A2 pass, stricter so previously allowed commands now need a permit or are blocked: Write/Edit/Bash writes to any `jade/*.py` other than the nine already listed (R-16), `git checkout|mv|rm` and `ruff format|check --fix`, `touch`, `chmod`, `vim` and `sed -i` on those files, `echo x > <any dir named jade>/hooks.py` (a directory called `jade` in an unrelated project is matched too), `launchctl remove|stop|kill|submit`, camelCase MCP tools whose name says set/write/create/execute (`setSetting`, `executeCommand`), `browser_run_code_unsafe`, a tool called with `action: start|stop|create|delete ...` when its name has no verb, `from jade import cli|ops|permits|improve|evals|ledger|decide` and `python -m jade.cli` in a command (SI-09), Ollama's port published on all interfaces or `bind`/`listen` on a wildcard in written content (SI-02), and a repeated command whose spelling differs from an earlier run with an unknown outcome (SI-07). `uv run python -c` programs are now read like `python -c`, so any rule that names a path or command inside them now fires. Looser: interface-only MCP tools (M-06a), and SI-02 no longer fires on a page URL or search term.
