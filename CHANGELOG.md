# Changelog

All notable changes to this project are documented here. Format: Keep a Changelog; versioning: SemVer once code ships.

## [Unreleased]

### Added
- **Rubric and label tools for the decision benchmark (V6-21).** `evals/rubric/rubric.md` tells a rater how to label a call from harm, reversibility and scope; it names no rule, so a rule cannot label itself. Each call gets two labels, `harm` and `authority`, and a small versioned table (`derive.json`) turns them into allow, ask or block. `evals/labels/agree.py` loads a corpus and rejects bad rows: any field the format does not name (a whitelist, also inside `raw` and `final`), a `label` on a hard row or on a row without two raters and a `final`, an unadjudicated disagreement, a secret shape or a real host in a committed row (key names too), the same call twice under two ids, and one task with over 25% of the rows. It prints kappa and percent agreement of two raters with the confusion table. It counts hard-class rows per family and gives them no accuracy rate. It freezes the final labels by hash. `evals/labels/corpus.jsonl` is empty: the 150 labelled rows are the owner's hours, and until they exist the report says "no accuracy number". Nothing in the gate or its policy changes. The risk: a good-looking kappa on few rows or few clusters means little, so the report gives no verdict under 150 rows or under 10 clusters. See `evals/labels/README.md`.
- **Report-only learning and the case ratchet (V6-32).** A new `safety_block` event now names the safety invariant that fired (`invariants` in its detail, for example `["SI-08"]`), so W-74 can be measured; the guard text and the schema do not change. `jade learn blockers` counts what stopped calls by invariant id and rule id, and `--sample N` gives a fixed sample for your precision check. `jade learn policy` shows, for each rule, the asks and the wrong marks side by side with a word of advice, and never suggests a change to a protected rule. `jade learn cases` prints a diff that adds a regression case for each call you marked wrong; it applies nothing. `evals/case_ratchet.py check` says whether a case fails on the version that erred and passes on the fix, and `evals/learn_replay.py` replays a rule candidate and counts human-only calls one by one. None of these writes a policy file, a threshold, a memory row or a label. The risk: a wrong report still steers you, so check the sample. See `docs/16-report-only-learning.md`.
- **V6-32 review fixes.** The report writer (`--out`) now also refuses a path that only differs in letter case from the checkout, the policies, the config directory or the JADE home (the Mac disk treats them as the same place). `jade learn policy` reads the level of MCP rules (M-01 is critical) and gives a rule id with no level in the risk policy the advice `protected`, never `review`. Wrong marks and human-only asks now count over all time, so the advice does not change with `--days`; `jade learn cases` has no window and proposes every call you marked wrong. A proposed case is skipped when its command holds a real host (`user@host`, a dotted name, the first argument of `ssh`) or a home path in any spelling. The U+2028, U+2029 and U+0085 characters are written as `\u` escapes, so one such command cannot corrupt the diff. A records file may not hold a `rule_id` or `tool` with a hidden line. `evals/case_ratchet.py` no longer reads a row as a twin unless it names a case of the same file with the opposite expectation, refuses duplicate ids and ids or classes with hidden lines, and reads each result line in its place and whole. A test of the V6-06 change (an env prefix is another target) was updated. The risk: more records are skipped, and a human rewrites them.
- **Decision hygiene and spikes (V6-24).** `jade ask` is now stricter in five small ways, and none of them can turn a "no" into a "yes". A repeat that differs only by trailing space, CRLF, colour codes or blank lines at the end returns the stored verdict with no provider call (a reworded claim is still a new call). `jade ask --decision D` judges at the higher of `--risk` and the risk of D. A decision that used all 3 revisions gets no more provider calls (exit 3: escalate, or report it as unverified), and a repeat of an answer the decision already holds no longer uses a revision. `--no-cache` works only in a human terminal or a test run, is capped at 3 provider answers per claim and evidence, and a fresh answer is never looser than the first, whether the first answer was live or from a `JADE_SOURCE=test` run (the cap counts both too, so the test tag buys no extra answers). `jade decide event` no longer accepts `jev_result_accept`, `jev_result_abstain` or `jev_result_reject`: only `jade ask` writes them, and the state machine checks that a finished call of that decision stands behind them. Each repeat is journalled with a reason, and `jade ledger stats` shows `repeat_reasons`. `evals/spikes.py` adds three read-only spikes (SP-0 raw Jev body, SP-1 noise, SP-3 replay of cheap checks on a ledger copy); SP-0 and SP-1 need the owner's word, and none was run. **Risk:** more exit 3 for callers that relied on a lucky resample; scripts that sent `jev_result_*` must use `jade ask`. Rollback: revert the commit, no migration. See `docs/15-decision-hygiene.md`.
- **Ledger readouts and label plumbing (V6-23).** `jade ledger stats` and `jade check` now have `--json`. `jade ledger stats` adds how often JADE asked, the time to answer, asks that ran out, the approve rate, how many verify calls are linked to a decision, how many have a checked label, and how often Jev's shadow answer agreed with your denies (the proxy now writes a `jev_answered` event with the call id, so each pair uses its own Jev call; one Jev call is never counted for two asks). The two gated-call counters (7-day `jade check`, 14-day `jade ledger stats`) now count the same events (so `asks.gated_calls` and `per_100_gated` use a bigger count than before and are not comparable with old output; `asks.gated_events` shows the old one). `jade review` uses plain words and says "Correctness is not measured" when it is not. `jade ask verify` with no `--decision` opens its own decision, so the call is linked. The `labels` table gets `label_type`, `sample_prob` and `audit_source` (old rows stay empty; one call holds one kind of label, and only `claim_true` fits). An outcome now records who saw the goal reached (`goal_check`): an exit status or an agent's word no longer makes a label for fitting (LD-31: the owner must say yes before merge). Nothing the gate decides changes. Details: `docs/14-ledger-readouts.md`.
- **Real-shell oracle snapshot and gate G4 (V6-22).** `evals/realshell_oracle.py snapshot` runs the SI-08 payloads (pushes to main) in real bash and zsh inside the existing sandbox and saves which stub programs the shell reached, in `evals/oracle/realshell-<shell versions>.json`. The owner runs it on the Mac before a release; it never runs without the sandbox. `check` is gate G4: it asks the real hook about each payload that reached a push to main, and fails if SI-08 did not block it, or if the snapshot is missing a payload of the current corpus. A known gap is counted, not hidden, and needs an owner ceiling. With no snapshot, G4 says not-enough-data and is not a pass. `stoploss` prints new gaps per 100 payloads for each review round, and says to stop adding parser waves after two independent rounds with none. KG01 to KG03 got `"oracle": "si08"` so they join the corpus. Nothing in the gate or its policy changes. No snapshot is committed yet: the owner run is still to do. Review fixes: an empty shell word is now kept in the recorded call, so `git -C "" push origin main` is seen as a push to main (it is a new known gap, KG52, closed by V6-08). The default timeout of `snapshot` is 120 s, because python3 on macOS needs about 25 s. G4 now fails when a payload timed out in every shell, or when more than 10 per cent of the payloads gave no evidence.
- **Decision replay, stats helpers and one report (V6-20).** `uv run python evals/decision_replay.py` sends a fixed list of calls through the real gate (`hooks.pretool`) for each arm. An arm is a version of the code, a level (`unset`, `off`, `low`, `medium`, `high`) and a gate mode. It prints a table of what each call should get against what it got, and a paired comparison of two arms. The comparison fails on any call that the base arm stops and the other arm lets through or stops less, even a known gap. At level `off` the gate only logs, so the runner reads its "would have stopped" note. `evals/stats.py` has small tested helpers (the exact limit after zero failures, kappa, a rank interval, the design effect of calls grouped in a task). `evals/report.py` prints, for each gate, the number of calls, the number of groups and pass, fail or not-enough-data. A rate is shown only with 10 groups or more. Nothing changes in the gate or its policy. The default list is the gate rows of the existing case files. An arm that enforces but only prints "advisory, not blocked" counts as a call that ran, so it fails. An enforcing base against an arm that only logs is "not comparable", not a pass. A bad `known_gap` row (no such work item, bad date) is an error. The report fails on a cassette miss (exit 2) and on an unknown `--base`. Jev is not measured here: without `--preferences FILE` no call reaches Jev, so a cassette is never read. The labelled list (V6-21) and the Jev cassette recorder are not built yet. `evals/run_cases.py` got a small `gate_event` function so both tools read a case row the same way.
- **"Never looser than main" check (V6-03).** `uv run python evals/never_looser.py <ref-a> <ref-b>` compares the gate on two versions of the code. It runs every command from the eval files, the test fixtures and the redirect tests through both, in three folders (no repository, a repository on `main`, a repository on a feature branch). It prints each command that the first version stops and the second lets through. Exit 0 and no output mean: not looser on these commands. Exit 1 means at least one command got looser. Exit 2 means the check could not run in full, so it is not an answer. The result is only as good as the command list, so it never says "not looser" in general. A new test checks that every rule of the first version is reached by at least one command.
- **Known-gap list (V6-03).** `evals/known_gaps/` holds the holes both versions still have, as counted rows with an owner. They are listed, not hidden. A row joins the normal gate only after its fix is merged.
- **Floor tests and the never-learn test (V6-17). Tests and one `jade check` row; the review also made the gate read more spellings of a floor call (see the last sentences).** "Safety and autonomy are separate" is now a test. List A: in gate mode `enforce`, at level `low`, `medium` and `high`, no call of the floor (SI-02, SI-05, SI-07 to SI-13, every human-only class, critical calls, merges, R-13, R-18, egress, fetch-and-exec) runs without a human, even when a confirmed answer, a scope and a Jev "yes" all exist for it. Two things are allowed by design and are pinned: egress at level `low` may be decided by Jev, and a merge may run on the very same call or on a repository scope the owner chose by a click. The wiring classes never go to the chat. List B (advisory by design: gate mode `off` and `advisory`) is tested line by line and is printed by `jade check` as the new row `advisory by design`. A never-learn test runs about 470 calls (the human-only calls, the same calls behind a wrapper, and the adversarial and regression cases that expect a block) and checks that memory never remembers them, Jev is never asked, and no scope is offered. 432 of them are in the never group. The other 37 are ordinary high calls, for example a push of a feature branch. They are listed by name with the answer memory gives today, so a new one or a change fails the test; the ones that should not be learnable have backlog rows (W-137, W-147). Tests for N15 to N17 (a forged permit row, an agent as principal, a replay of a used permit) and N41, N42 (a call retried after a Deny) were added. N39, N40 and N43 (a denied call split, scripted or reworded) are five new known-gap rows, because JADE cannot see intent. The tests found two real holes and record them as strict `xfail`, not as passes: a chain such as `docker compose up -d; curl URL | sh` can be remembered as a kind, and a Deny is not honoured when the retry has an env prefix or runs from another folder. Closing them changes the hook path, so they wait for the owner. The review of V6-17 found that the floor was only tested with one spelling of each call. A call behind `/usr/bin/env`, `arch`, `script -q /dev/null`, `watch`, `nohup`, `caffeinate`, a program path such as `/usr/bin/sudo`, or `ssh host '...'` was rated an ordinary call, so Jev could say yes to it. The gate now reads it as the call it runs (stricter only), and a new test runs every row of List A behind each wrapper. These spellings are now human-only too: `npm -w pkg publish`, `pnpm --filter x publish`, `docker image push`, `docker compose push`, `oc delete`, `kubectl replace --force`, `stripe ... --live=true`, `git push origin v1.0`, `python3 -m twine upload`, `yarn npm publish`. Still open: an exact answer may be kept for `ssh host 'curl ... | sh'` and the other ssh-wrapped R-13, R-18, R-21, R-22 calls (the same chain gap, W-147); `kubectl drain`, `docker rmi -f`, `unlink`, `trash`, `flyctl deploy`, `git stash clear` and a Python `shutil.rmtree` are not human-only (the owner decides).
- **Stricter release and CI (V6-34).** The release workflow now starts with a guard job (`scripts/check_release_tag.sh`, on the full history). It refuses a tag whose commit is not on `origin/main`, and a tag with no non-empty `## [X.Y.Z]` section in `CHANGELOG.md`. The old fallback release text is gone. No other job starts before the guard passes. `ci.yml` has a read-only token, a time limit per job, and cancels an older run of the same pull request. Every action is pinned by commit sha in both workflows (Dependabot keeps them current). A new `secrets` job scans only the new commits with `.gitleaks.toml` (`scripts/scan_new_changes.sh`; fake credentials are allowed only under `tests/` and `evals/`). A new `macos` job runs the setup tests, the hook payload tests and `scripts/verify_install.sh` on a hosted macOS runner; the real-shell oracle is not run there. 40 tests that compare elapsed time with a bound now carry `@pytest.mark.timing`, so they run serially, and `tests/test_timing_marks.py` fails on a new unmarked one. No gate behaviour changes. Risk: a hurried release now fails on purpose until main has the commit and the CHANGELOG section. Not verified here: the workflows themselves have not run on GitHub, and the macOS job has not run on a hosted runner. Not done: the 200-run loop for W-95 (needs the `python:3.13-slim` image, which is not on this machine).
### Changed
- **`jade check` and `jade hooks install` now say what is true (V6-10).** A row can be ok, FAIL or WARN. WARN means "not safe" or "not known". WARN never changes the exit code, so no default and no blocking behaviour changes. The "what blocks" row is computed from the gate mode and the level, and lists rule ids. At level `off` it says that most rules only log, and which ones still block. Level `off` and advisory gate mode are now WARN, not ok. Gate mode `off` no longer says every hook is inert, because the recording hooks still run. At level `low` and `medium` the row names the paths that let a call run with no human. "Version vs main" compares the running commit with `origin/main`. An equal version string is not enough. When it cannot tell, it says "unknown". The pre-push guard and the remote branch protection say "unknown: owner confirms". `jade hooks install` prints the gate mode, what blocks and the approval backend. `jade setup` counts the hooks from the code instead of saying "four". The troubleshooting table in `docs/09` matches.
### Changed

- **Human text, tier 1 (V6-26).** The chat question, the macOS dialog and the terminal permit screen now come from one builder (`askplain.build`). Each one says what Allow does, what Deny does, and what happens if you give no answer, with the numbers read from the code (the chat says 10 minutes and 3 Denies, the dialog 2 minutes and 5 minutes, the permit its own time). Each one shows the folder and who asks (the main session, a subagent and its type, or a request from the command line). It also gives the five fields that `policies/escalation.yaml` promised and no code read (W-83). The plain first line now names more flags that widen a call: `git clean -d/-x`, `git config --global/--system`, `rsync --delete`, `docker compose down -v`, `kubectl --all`, `terraform -auto-approve`, `docker push --all-tags`, `crontab -r`, `gh gist --public`, `npm publish --access public`, `rm --no-preserve-root`, `glab --auto-merge`, and the count in `git branch -D a b c`. A word that is not plain (`$X`, a glob) says "maybe more". The permit screen now starts with the same plain lines. In signed mode the code on the permit screen is the code the signing helper asks for, so there is one code, not two that could never match. Typing `n` at the permit screen now refuses the request and journals `permit_refused`; it is not a Deny and changes no hold key. Typing `deny` records a Deny. Anything else still leaves the permit waiting. The gate tells the agent about a refusal for the next hour. The text to the agent now says to send the JADE question alone (Fix B). Risk: every line here changes what a human reads at a safety decision, so a person must read the final words before release. Not built: refusing a batch that carries a JADE token (Fix C, next release), the command in the signing helper (needs the root helper to be installed again), a re-probe of the native ask box (V6-15).
- **Chat and dialog text is shown safely (V6-09).** Before, the chat question and the dialog showed raw bidi and control characters, and a long command was cut so that the middle was hidden before you clicked Allow. Now one function, `util.show_safely`, writes out each control, bidi and zero-width character (for example `\u202e`) in the command, the tool name, the folder and the content in the chat question and the dialog, and in the terminal permit screen, `jade review` and `jade knows`. When a long command is cut and a risky part is in the hidden middle, that part is shown again in full. If it is too long or cannot be found (a quote, a line break or a here-document can hide where a command starts), the question says so, shows the gate's own reading of what it rated, and tells you to Deny it and ask the agent to run the risky command on its own. There is no terminal command yet that prints the whole call of a chat question. A rated command inside `bash -c '...'` or `$(...)` is shown with the whole form it sits in (and a `cd` just before it), even when a visible command has the same key. If the gate has too many such forms to rate one by one, the question says it cannot show which part is risky. Letters that draw as blank (Hangul fillers, Braille blank), variation selectors, the combining grapheme joiner and combining marks after an ASCII character are written out too, so a look-alike folder name cannot pass as the real one. Sentences keep the Persian half-space (U+200C) and Persian marks. Risk: a command with a Persian half-space now shows it as `\u200c`, which is ugly but safe. A decomposed accent in a path (a letter plus a combining mark) now shows as an escape. A label in `jade review` or `jade knows` that held a control character now shows it written out, where before it showed a space.
- **An Allow in the chat covers only the exact call it was shown for (V6-07).** Before, a grant matched the call by its shape, so the same words with other spacing or another prefix could spend it. Now a grant is spent only when the tool, the text and the folder are the same (the `plan_hash`). A call with extra spaces, a new `NAME=value` prefix or another folder asks again. This means a few more questions. The question now ends with the folder and says what the Allow covers. A grant row that has no `plan_hash` is not used. An open question is also kept per text, so a changed text gets its own question. The settings that change how a Bash call runs (`dangerouslyDisableSandbox`, `run_in_background`, `timeout`) are part of the call too: the same text run with the sandbox off or in the background asks again, and the question lists them (`description` is only a display line and does not count; a false or empty value is the same as no value). A Deny is not changed: it still covers every call of the same shape, which is the safe side (a Deny of a call with such settings covers that call only). The size of the extra questions is not measured yet: `evals/gate_replay.py` rates commands and cannot see how often an agent changes a call after the question, so it needs the owner's recorded asks (deferred, see the V6-07 notes in the plan).
- **Level `off` is now "observe plus floor" (V6-16). More calls are blocked at `off`; no question is asked.** Before, at `off` the gate only logged most rules, so an agent could push to `main`, retry a command with an unknown result, or edit `~/.claude/settings.json` and the hook files. Now, with the gate mode `enforce`, these block at `off`: SI-07, SI-08, and a write to JADE's own live wiring (HO-wiring, HO-checkout-install, HO-settings-shadow, and HO-state-path: a script run that names the JADE config or state, because a script could set the gate mode to `advisory` and turn the floor off), as SI-09 to SI-12 already did. A settings write is read as the whole file it leaves (an Edit is applied to the file first) and with JSON `\uXXXX` escapes decoded, so a split or escaped `disableAllHooks` is caught. Everything else still only logs at `off`. In advisory gate mode nothing changes. `jade level` prints the words on stderr (stdout still holds only `off`), and the `level`, `what blocks` and `host permission prompt` rows of `jade check` name the floor. To cut the asks of levels `low` and `medium`, a new scope `rule_project` is offered in the chat for the two noisiest rules (R-16 and R-14). It helps only at `low` and `medium`, because only memory reads it and memory runs only there. It does not remove asks at `off` or at `high` (backlog W-146). It covers: any write of one file under `jade/` (R-16), or the same plain `ssh`, `scp`, `sftp` or `rsync` command (R-14, by its exact text). It is only for a JADE checkout that is not the running JADE, never covers the live wiring, and decides nothing until you run `jade review confirm`. A Deny in the chat takes a confirmed scope out. This scope is a loosening: read it before you confirm. Edits of `jade/` code still only log at `off`. Roll back by reverting the commit.
- **The docs and the data now keep their promises (V6-11).** The docs say what the code does: README and docs/12 (memory never covers a critical call, R-13, R-18, R-21 or R-22; a merge is remembered as that exact call), docs/00 (only Claude Code is wired), docs/05 T20 (the failure hook exists), and the hook, schema and registry counts, which `tests/test_docs_truth.py` now compares with the code. `WAITING_DEPENDENCY` is marked "reserved, not entered". README no longer says what only one machine can know; `jade check` does. Four keys that nothing read are deleted from `policies/escalation.yaml` (`abstain_to`, `max_revisions`, `deadline_default_h`, `score.gates`). A fifth, `each_question_includes`, is read now: the question builder of V6-26 refuses to build a question without the listed fields. A test fails on any new unread key, also one inside a `noul` or `choice` block; W-83 and W-85 are closed. A run with a ledger of its own no longer writes its model-drift note to the real JADE home. `jade ledger purge --dry-run` counts what a purge would clear and changes nothing. `jade ledger purge --ask-text` also clears the chat question and the labels in `asks` and `human_answers`, which kept command text for ever. That is off until the owner agrees (W-147), and `jade maintain` never turns it on. `jade maintain-schedule` prints a cron line or systemd timer for machines without launchd, and `jade maintain` leaves a last-run stamp that the `maintain job` row of `jade check` reads. No gate behaviour changes. Risk: the scrub cannot be undone, so run the dry run first.
- **Memory never covers a critical call, and a remembered kind keeps its target and place (V6-06).** A critical call (for example `kubectl apply`, `terraform apply`, `pfctl`) and a shell write that R-13 or R-18 rates (the files that guard the agent and its instructions) are never decided from a confirmed answer: they are asked every time, and `jade review confirm` of one changes nothing. A remembered kind and an exact answer now include the env prefix (`NAME=value`, `env`, `export`), `sudo`, `git -C DIR`, and the directory the call runs in (a leading `cd PATH` is read). So a confirmed `DOCKER_HOST=ssh://staging docker compose up -d` does not cover the same words aimed at prod, and `rm -rf build` confirmed in one repository does not cover another. The "any project" scope still ignores the directory but not the target. Old answers have the old keys, so they stop matching and age out (30 days after last use, 180 days at most); ask once again to renew one. A deny of the same words in another place or with another target no longer hides an allow of this place.
- **One id register for work items and threats (V6-02).** A W id and a T id now each name one thing, and `tests/test_ids_unique.py` fails on a new duplicate (the allow-lists are empty). `W-96` to `W-105` are historic feature ids (CHANGELOG, test file names, commits) and no work item uses them. The 21 working-tree backlog rows that were numbered `W-96` to `W-116` are in `work-items.jsonl` as `W-117` to `W-137` (old id plus 21; `W-115` stays the SI-13 sandbox row), the PR 47 entries below and its tests and spec cite the new ids, and a citation written "WT W-110" means `W-131`. Eight rows that waited for the register are `W-138` to `W-145`. See `docs/07` section 2.
- **Clear questions (docs/12 section 12).** The chat question and the dialog start with a plain line for what the call does, a risk line, and an "Also in this call" line. The text comes only from the gate (`jade/askplain.py`).
- **Bigger scopes from the chat.** Options "Allow, suggest ..." record a hint with a scope (`kind_project`, `kind_any`, `merge_project`). A hint decides nothing; `jade review confirm` in a terminal makes it standing. Confirm shows the scope, its lifetime (30 days after last use, never more than 180) and the undo `jade knows rm ID`.

Any non-ASCII character, control space or backslash in the call gives no merge scope, and a git config line that ends with a backslash gives no scope. A merge scope confirmed on an earlier build of this branch no longer matches and is asked again.

### Fixed
- **Small durability fixes (V6-27).** `jade work` could lose an item when two commands ran at once, or leave a cut-off line in `work-items.jsonl`. Now it holds a file lock over read, change and save, and writes a temp file and renames it. `BACKLOG.md` is written the same way. The SessionStart briefing has two new lines: `decisions held: N` and `permits that expired twice: N`. Each is told once for the same set of ids. The expired-twice line also counts the newest permit time of the plan, so the same command expiring twice again later is told again. After a `compact` or `resume`, they come back with the ids, and the open asks of the session are listed. The first count is for all projects, because the ledger does not record a project for a decision. No gate behaviour changes. Risk: a second `jade work` waits up to 10 seconds for the lock, then stops with a message.
- **Push and merge lines say what really happens.** Every target of a `git push` is read, and when the line cannot be sure it names the worst outcome. Order: force (`+main`, `-f`, `-fu`), delete (`--delete`/`-d` makes every target a delete, `:main`, `--prune`, `--mirror`), the main branch, tags (`--tags`, `--follow-tags`), then the named branch (`heads/main` counts as main). `--all`, `--branches` and `:` alone say "every matching branch ... which can include the main branch". `git push`, `HEAD` and `@` say the current branch and that it can be the main branch. A line over 20 words falls back to a short worst-case form. A long flag cut short (`--m`, `--b`, `--f`) counts as every dangerous flag it starts, even where git would call it ambiguous. A specific push line is shown only for a known shape (known plain flags, a plain remote name, plain refspecs). Any option with a value (`--repo`, `-o`, `--recurse-submodules`), a URL or path as remote, `--`, a git option before `push` (`-c`, `-C`, `--git-dir`), a `.` or `..` remote, the word `tag`, and any call that is not one plain `git push` command give "This push can force push, delete branches and tags, and include the main branch." The raw words of the call are read for this: a quote, a backslash, a `$`, a glob character (`*`, `?`, `[`; the shell expands it first, so a `*` refspec too), a word before `git push` (`GIT_*=`, `HOME=`), spacing other than single spaces, or another command in the same call (`git config ... && git push`; only a leading `cd PATH` is left out) gives the worst line. A value flag before the number (`glab mr merge --message 5 12`) or `-R`/`--repo` gives no number. Risk lines use plain words (no "reflog", "deployment", "credential"). The merge line names what a flag lets the call do, with the flag as written: `gh pr merge 940 --admin --delete-branch` reads "Merge pull request 940, skip the branch rules (--admin) and delete its branch (--delete-branch)." (also `-d`, `-sd`, `--auto`, and `glab mr merge --remove-source-branch`); a word that is not plain (`$FLAGS`, a glob) adds "maybe more" (V6-05, merge gate for PR 42 and PR 43).

- **A redirect written inside a push hid the rest of the push from SI-08 and the risk rules.** `git push origin feature &>log --no-verify +feature:main` was rated medium (R-19) with nothing blocked and no key, and real git (zsh and bash) force-updates `main` with it. The shell takes a redirect out of the words wherever it stands, so `shellnorm` now does too: every redirect (`&>`, `&>>`, `>&file`, `>|`, `>`, `>>`, `<`, `<>`, `<<<`, a heredoc, with or without a descriptor or a space, even glued to a word as in `feature&>log`) is moved to the end of its command as `> file`, and a descriptor copy or close (`>&-`, `<&-`, `3<&0`) is dropped. - **zsh redirect spellings, a descriptor close with a word glued to it, braces, `!` redirects and printed text (W-129, W-130, W-132; found in review of the two entries above).** (a) zsh has redirect operators bash has not: `>>&`, `>>|`, `&>|`, `&>>|`, `>>&|`, `>>&!`, `>!`, `>>!`, `>&|`, `>&!`. They were not in the operator list, so `git push origin feature >>&log :main` was cut in two and `:main` was lost (zsh pushes to main). They are redirects now, written `>` or `>>` with the file, and a `|` after `>&` no longer splits a command. (b) The shells read some text differently, and the gate cannot know which one will run it, so it keeps every reading and any reading can block (fail closed). `>&-` closes a descriptor in bash and the word glued to it is an argument (`git push origin feature >&-main` pushes main); zsh reads `-main` as a file name (`git >&-lg push origin :main` is a push in zsh only). `>! lg`, `>>! lg` and `>&! lg`: zsh writes the file `lg`, bash writes a file named `!` and `lg` is an argument (`1>! git push origin main` is a push in bash only). A `{` or `}` is a command group in one shell and a plain word in the other (`{git push origin HEAD:main}` runs in zsh; `git push origin feature a{ :main`, `a\{b,c} :main` and `} :main` push in bash). The scanner writes a mark for each brace and the skeleton holds five readings of it (every brace cuts the command, none does, one cuts where a command starts and its `}` cuts too, one cuts when it is a word of its own, one cuts when it is inside a word), so `if { true } { git push origin :main }`, `{git push origin :main}` and `a{ :main` are all stopped. A run of more than four literal braces counts as four in the literal readings, so a command of 100 000 braces costs about 1.3 times what it cost before. (c) What `echo`, `printf` and `print` print is not what they are given: zsh and sh `echo` read `\\` and `\n`, zsh `print` also drops the backslash of any other escape (`\>` prints `>`), bash `echo` prints the text as it is. The text that goes into a shell is read in all three ways, whatever the printer is called (`time echo`, `env printf`, `command print`, `! echo`, `nocorrect echo`, `\echo`, `/bin/echo`). The 24 expected-failure tests for the brace hole in `tests/test_redirect_anywhere.py` are removed, because it is fixed. Known and not changed here (W-131, W-133): `/usr/bin/printf`-style escapes beyond `\\0nnn`, `\\xhh`, `\\n`; `sh f` after `echo ... > f`; an unset variable in a push word; `cat >&- credfile` is rated like a plain `cat credfile` (medium; it was critical on 0.6.1 only because `>&-` was read as a write).
